# 部署案例：多地区转发链

一次与旧系统并行上线的真实部署：5 个节点、3 条深度递增的转发链、4 条 NAT 单跳入口，
外加 1 条指向旧代理服务的入口。上线当天旧系统全程未中断，7 条入口的 TCP 与 UDP 共
14 项验证全部通过。

本文与配套清单 [`examples/inventory.case-multi-region-chain.json`](../examples/inventory.case-multi-region-chain.json)
是**脱敏副本**：可以直接渲染，不可以直接部署。

## 脱敏说明

先说清楚哪些是假的、哪些是真的，再看配置。

| 内容 | 处理 |
| --- | --- |
| 全部 IPv4 | 换成 RFC 5737 文档保留地址，**不指向任何真实主机，请勿扫描或连接** |
| 节点名、TLS `server_name` | 换成中性占位名与 `.example` 保留域名 |
| 端口号、监听器名、`ingress_interface` | **保留真实取值** |
| 凭据 | 清单里本就没有。TLS 只以路径出现，证书与私钥不在本仓库 |

地址的分段方式保留了真实部署的一个事实：`region-a` 与 `region-b` 同属一个服务商网段，
`region-c` 与 `region-d` 各自独立。第四段按拓扑位置递增——这种整齐的编号本身就说明它们是
构造出来的。

**端口为什么不换。** 这份设计的助记线索是「入口端口号即链路编号」：`65011` 在入口机、
在 `region-a`、在 `region-b` 上是同一个号，监听器名直接内嵌它（`entry-65011`、`relay-65011`）。
换号就要连带改名，读者会失去读懂五节点配置的唯一抓手。端口不是凭据，且全部 ≥1024，
正好佐证 README 里「非特权 `sbpd` 账户需用高端口」这条要求。

## 拓扑

```text
用户 ──► entry（enp3s0f0，masquerade，不跑 GOST）
          │
          ├─ 65001/tcp ─────────────────────────────► 旧 SOCKS5 198.51.100.99:19998
          │
          ├─ 65002 ─► region-a:64999  ┐
          ├─ 65003 ─► region-b:64999  │ 纯 NAT 单跳，直达各自 sing-box
          ├─ 65004 ─► region-c:64999  │
          ├─ 65005 ─► region-d:64999  ┘
          │
          ├─ 65011 ─► region-a:65011 ═► region-b:65011 ─► 127.0.0.1:64999
          │
          ├─ 65012 ─► region-a:65012 ═► region-b:65012 ─► 127.0.0.1:65022
          │                                                └═► region-c:65012 ─► 127.0.0.1:64999
          │
          └─ 65013 ─► region-a:65013 ═► region-b:65013 ─► 127.0.0.1:65023
                                                          └═► region-c:65013 ─► 127.0.0.1:65023
                                                                                 └═► region-d:65013 ─► 127.0.0.1:64999

          ═► 表示 relay + mTLS：一条 TCP 连接内复用，同时承载 TCP 与 UDP
```

| 入口 | 路径 | 落地 | 经过节点数 |
| --- | --- | --- | --- |
| `65002`–`65005` | NAT 单跳 | 各自节点 | 1 |
| `65011` | region-a → region-b | region-b | 2 |
| `65012` | region-a → region-b → region-c | region-c | 3 |
| `65013` | region-a → region-b → region-c → region-d | region-d | 4 |

## 设计要点

### relay 只跑 TCP，续链必须落回环

渲染器强制 relay 的 `protocols` 恰为 `["tcp"]`，且 relay 止于它的**固定 target**。
mTLS 通道在一条 TCP 连接里复用，同时承载 TCP 与 UDP 载荷（README：MTLS 是多路复用 TLS，
不是双向证书校验）。要让链继续往下走，就必须把流量交还给一个重新同时拥有 TCP 与 UDP 的东西——
这正是 `relay-65012 → 127.0.0.1:65022 → forward(tcp,udp) → chain region-c:65012` 在做的事。

**回环端口是协议再展开点，不只是多一跳。** 可直接复用的推论：链能有多长，只取决于你愿意
分配多少个回环桥接端口。

### allowed_sources 为什么长这样

同一份配置里能看到四条不同的规则：

1. **第一跳白名单写的是入口机的出网地址，不是它的网卡地址。** 入口机做 masquerade，
   `region-a` 永远看不到它的内网地址。这是这种拓扑最容易踩的坑——写错了不会报错，
   只会在 admission 处被静默拒绝。
2. **每个 relay 只放行一个上游，不写网段。** `region-b` 只放 `region-a`，`region-c` 只放
   `region-b`，`region-d` 只放 `region-c`。链的方向因此由 admission 强制，而不只是配置意图。
3. `127.0.0.1` 到处出现，不是链路需要，而是为了本机诊断不被 admission 拒掉。它不增加外部暴露面。
4. **回环桥接完全不带 `allowed_sources`。** 校验器允许这一点，仅仅因为它们绑在回环上——
   白名单是公网绑定的补偿控制，而回环绑定已经由内核限定了作用域。

### 端口编号约定

公网跳全程同号；回环桥接另用一段（`650xx` 对 `652xx`），所以桥接端口不可能被误认成公网端口；
每条链末端的 relay 恒指向本机固定端口。这套约定与具体数字无关，可以照搬。

### 写错一个 chain.host 会静默改路

注意 `region-b` 的 `bridge-d` 指向的是 **`region-c`**`:65013`，不是 `region-d`——末端是
**经由**第三跳到达的。工具无法替你判断这是不是你想要的：它不做跨节点一致性检查，
也不知道你心里的拓扑。**清单是这个决定唯一被写下来的地方。**

这也是「校验器不检查什么」的诚实说明。同类的还有：证书是否存在与是否过期、
目标端口上是否真有服务在听、云防火墙、端到端连通性。

### 与旧系统并行意味着什么

每项隔离手段对应一个被退掉的风险：

| 手段 | 退掉的风险 |
| --- | --- |
| 独立 `ip sbpd_nat` 表，优先级 −101/99 | 新规则先于常规 NAT 链运行，但只匹配清单声明的新入口，旧表全程未被触碰 |
| 每台把既有监听写进 `reserved_listeners` | 端口冲突在渲染时就失败，而不是部署后才发现 |
| 保留 `entry-65001` 指向旧服务 | 证明新表可以承载**旧**目标，而完全不用编辑旧表 |
| 独立二进制 / unit / 配置路径 / 服务账户 | 新旧两套可以同时运行、分别停启 |

## 上线与验证

| 检查项 | 方法 | 这条证明了什么 |
| --- | --- | --- |
| 7 条入口 × (HTTPS + 真实 UDP DNS) = 14/14 | 逐条起临时本地客户端 | 每条链的 TCP 与 UDP 都通 |
| 出口 IP 与预期落地节点一致 | 出口检测服务 | 流量确实从预期的节点出网 |
| 两次独立构建产物逐字节一致 | 比对摘要 | 可复现构建，产物可审计 |
| 旧服务 PID / 状态 / 配置摘要不变 | 上线前后各采一次 | 旧进程未被重启或改写 |
| 旧 NAT 表不变 | `nft list table` 前后比对 | 新表未污染旧规则 |
| 每台主机留有安装前备份 | 上线前生成 | 有回退依据 |
| 五台重新渲染比对，漂移为零 | 事后复核 | 线上状态与清单一致 |
| 更新与回滚编排四条路径各验证一次 | reload、restart、控制面审批、失败自动回滚 | 变更流程本身可用 |

### 这些检查没有证明什么

出口 IP 检查能证明**落地节点**，但**无法区分路径**：`65003`（单跳到 region-b）与
`65011`（经 region-a 到 region-b）的出口地址完全相同。路径要靠时延差异和各跳侧的日志佐证，
不能由出口检测代劳。

渲染器本身也不验证任何运行时状态——它只生成配置。上面这些检查全部由外部执行器完成。

## 复现

```bash
python3 sbpd.py render \
  --inventory examples/inventory.case-multi-region-chain.json \
  --output output/case
```

产出 11 个文件：入口机只有 NAT 三件套（`sbpd_nat.nft`、`apply-nat.sh`、NAT unit），
四个落地节点各只有 GOST 两件套（`gost.json`、GOST unit）。每个节点只拿到它需要的东西。

渲染是纯校验加文本生成，不联网、不读证书、不产生任何凭据。

## 照搬时必须改什么

- **全部 IPv4**，并注意第一跳白名单要写**出网地址**而不是网卡地址
- `ingress_interface`：用 `ip -o link` 查你自己的网卡名，不要照抄
- 你自己的 CA 与内部 `server_name`；证书与私钥不经过本工具
- **用 `ss -lntup` 在你自己的主机上重新普查 `reserved_listeners`**，不要照抄本案例的七个端口——
  它们描述的是这次部署的主机上恰好在听的东西
- `64999` 换成你的 sing-box 端口，并让它绑 `0.0.0.0`，这样直连与回环两种到达方式都能服务
- 所有由本工具渲染的端口保持 ≥1024（`reserved_listeners` 不受此限，它描述的是别人的服务）
- 入口机需要 `net.ipv4.ip_forward=1`

## 本案例不包含什么

不含 sing-box 自身的配置、不含证书与私钥、不含用户与订阅、不含部署执行器。
本工具只负责把清单渲染成 GOST / nftables / systemd 配置；身份归属属于 manager，
安装、校验与回滚属于外部执行器。

配套的 [`examples/identity-pool.example.json`](../examples/identity-pool.example.json)
只是用来说明「私有执行器读进去的身份清单是什么形状和规模」，**本工具不读取它**，
其中 300 条凭据全部由 [`examples/make_identity_pool.py`](../examples/make_identity_pool.py)
以固定种子重新生成，与任何真实部署无关。
