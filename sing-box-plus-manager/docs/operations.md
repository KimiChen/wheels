# 运维：主控发布、节点变更手册、维护窗口与前置条件

> 本文是 [`../README.md`](../README.md) §4.6 / §8 的展开。
> 除节点契约外，绝大部分条目来自组织内一套已在生产运行的同类主控的经验总结——
> 每一条后面都有一次真实故障，所以写的是「必须」而不是「建议」。

## 1. 节点前置条件

上线一个节点之前先核对这几项，否则后面每一步的症状都会指向错误的方向。

### 1.1 NTP 是硬前置（C27）

Shadowsocks 2022 的握手带时间戳防重放。一台时钟慢约两分钟的节点会让**所有**用户握手失败，
日志里只有一句时间戳无效。表现是「整节点不可用」，很容易被误判成网络或配置问题——
实际只需要装一个时间同步服务。

主控把**节点时钟偏移**作为一等健康项采集并告警，不要等它以其他形式暴露出来。

### 1.2 监听地址

节点进程若只绑公网地址，本机 loopback 上的既有链路会拿到 `connection refused`。
症状很有迷惑性：直连的入口全部正常，只有经过本机中转的那几条挂掉。
需要同时承接公网与 loopback 时，绑 IPv4 wildcard。

### 1.3 上一跳 admission

节点侧只放行上一跳的固定公网 IP。这与主控出口 IP 是同一类约束，
合并进 README §10 R5 统一管理：**出口 IP 是一等配置项**，
多出口或动态 NAT 必须提前登记全部出口。

### 1.4 systemd 两个会直接炸的坑（C28）

- **只访问本机 socket 的辅助 unit 必须 `PrivateTmp=false`。**
  否则 systemd 给的私有 `/tmp` 会把宿主机的 socket 藏起来，表现为「本机连不上本机」。
- **进程要同时穿过两个权限档次时，主组与补充组缺一不可。**
  agent 需要主组用于一档 socket、补充组用于另一档（C18 要求两档不许合并）。
  缺主组则 socket 建不出正确属组，缺补充组则穿不过隔离目录——**两种都表现为「服务起不来」**。

目录权限可直接参照 `shadowsocks-rust-plus/packaging/*.sysusers` 与 `*.tmpfiles`：
`0751` 的共享父目录 + `0750` 的分组隔离子目录，那里的注释写明了为什么父目录用 `0750` 会破坏穿越。

## 2. 主控自身的发布器

> 这一节讲的是**部署 sing-box-plus-manager 这个应用**，不是分发节点配置——
> 节点配置分发已按 D20 移出主控，见 §3。


### 2.1 基本形态

- **dry-run 默认，`--apply` 显式。** 没有 `--apply` 的调用不得产生任何线上状态变更。
- 固定一个**精确 HEAD**，从该 commit 构建不可变本地快照；门禁通过后**不再读可变工作树**。
- 网络传输只写**特权私有 stage**；取得部署锁后才把 stage 增量同步到活动目录。
  两次并发 apply 因此不会混出一个半新半旧的目录。
- 变更脚本本身不做下载：源清单是唯一可读取的来源，复制每个文件前再次核对摘要，
  拒绝清单外条目、拒绝路径中的任意符号链接。
- `--apply` 即使全部门禁通过，也**不自行 reload / enable / start / stop / restart 服务**——
  状态变更留给显式的、有人看着的那一步。

### 2.2 中断恢复 marker

任何一次会改动活动配置的事务，开始前先刷盘一条 marker，记录：

```text
命令 · commit · 站点/节点 · 原始备份路径 · 目标的 before/after 摘要 · 服务的期望状态
```

- 中断后**只允许用相同命令 + 相同 commit** 复用原始备份向前收敛。
- **不得手工删除 marker，也不得清理它引用的备份。**
- 全部健康检查通过并刷盘后才删 marker。
- 若失败原因需要改发布器本身，**待处理的 marker 必须拒绝新源码接管**，
  另走一次显式审批的迁移流程——不能删掉 marker 然后从半安装现场建立新基线。

### 2.3 退出码不是健康证据（C22）

不要相信包装器或面板的 `status` 退出码。校验 PID 文件 + 进程身份（`/proc` 或等价机制）。

> 生产教训：健康脚本用原始二进制路径去匹配被面板改写过的进程标题，
> 导致**连续两次误回滚**——其中第二次现场的 HTTP 检查实际已经全部通过。
> 改成 PID 文件加存活探测后第三次才成功。

同理，reload 之后的健康检查要给新 worker 留接管时间窗（经验值 10 秒），
否则会把旧 worker 的瞬时响应误判成新版本故障。

### 2.4 回滚

- **必须整组恢复**：配置 + 数据 + 指针作为一组，不能只切一个指针。
  只切指针会让新代码读到旧配置，或者反过来。
- 保留上一个已验证版本及其自带的配置快照；**不在新旧代码之间共用可变配置**。

### 2.5 建库不与应用发布绑定

**本项目没有迁移**（D22）：`schema/` 下的 DDL 一次性建出，schema 变更靠重建数据库。
所以下面这条生产教训换了落点，但没有失效。

> 生产教训：把迁移绑在一次应用发布上，那次发布顺带引入了一个无关改动，
> 健康检查因此失败，门禁把**已经成功的迁移一并回滚**。
> 拆开之后同样的迁移一次通过。

同一形状在本项目是：**建库与发布回滚不得共用一个门禁**。
库已经建好之后，发布失败不得连带删库——那会把一次可回滚的发布变成一次数据丢失。

建库本身的纪律：

- 建库在**一个事务**里完成：建到一半失败不能留下「部分建好」的库，
  那是一致性门禁最难判断的状态；
- 一致性门禁精确比对表集合：库要么是空的（建全套），要么与期望**完全一致**（放行），
  介于两者之间失败关闭；
- 有了必须保留的账本之后，要重估的是 D22 本身，而不是在建库器上补一个半吊子的升级路径。

### 2.6 发布后收敛核对

不看日志说「成功」，而是核对可观测的事实：

- 活动目录的属主与权限符合预期，**属主异常的文件数为 0**；
- 无残留 stage；
- 健康探针返回**精确**的状态码（不是「2xx 就行」）；
- 本地、线上、镜像三方的内容摘要一致；
- 开放告警数为 0。

## 3. 节点变更手册（排空五步）

**主控不编排这套流程（D20）**，它由运维在节点上执行。主控只参与两类操作：
第 3 步的最终采集与入账确认，和第 5 步的 runtime 登记。

按 C19，计划内重启必须走这五步，**不能 `systemctl restart`**：

1. **停止接入新连接**。用固定的下线/防火墙钩子，
   **不能先发 SIGTERM 再去抢最后一次快照**——进程可能在快照采到之前就退了。
2. **等会话归零**：轮询快照的 `tcp_sessions` / `udp_sessions` 至 0，或超时。
   这是这两个 gauge 唯一的用途（C6）。
   gauge 读取失败或字段缺失时只能按固定超时，**并无条件把该窗口标记为未排空**。
3. **采集并确认确切的最终快照**：保持下线措施，调用 `POST /nodes/{id}/collect`，
   请求体带当前进程的 `expected_runtime_id`。原始快照持久化后取得 `runtime_id / sequence / payload_sha256`
   回执；若实际 runtime 不匹配则拒绝，不得把新进程的快照当作旧进程尾账。
   然后调用 `GET /nodes/{id}/settlement-status`，三个字段全部作为必填查询参数。
   **正常停机门禁是该批次 `applied` 且该快照的所有 session gauge 为零**，不是成功采集或较早批次已入账。
   等待超时或状态不明时停止正常流程；确需强切则显式记录未排空、未闭合及可能丢尾。
4. **核对仍是回执对应进程，再停进程、换配置、起新进程**。新进程是新的 `runtime_id`，累计值清零，
   额度是内存态也一并丢失。
5. **登记新 runtime 并先恢复零额度**：在主控登记 runtime 与首快照策略，
   下发全零安全表，**健康结算通过后才恢复正额度**（C33）。
   受限节点必须已配 `startup_action=deny`，否则第 4 步之后到第 5 步之间是无限放行。

强切时已持久化入账的字节仍保留，尚未入账的内存尾账可能丢失；该窗口必须标记为**未排空**并披露缺口。

**只读确认的响应契约**：回传请求中的 `runtime_id / sequence / payload_sha256`、对应 `batch_id`、
`status` 与 `drained`。摘要是解压后原始快照字节的 SHA-256，不对重序列化后的对象计算。
`status` 复用持久化批次状态：`pending / applied / rejected / superseded / conflict`；
找不到完全匹配的批次返回 `unknown`，参数缺失或格式不合法返回 400，查询失败不能返回 `applied`。
`unknown` 的 `batch_id / drained` 均为 null；已知批次若缺少可信排空证据，`drained` 也为 null，不猜为 true。
只有该批次的账本、累计、游标和批次状态已原子提交才能返回 `applied`。
`drained` 来自同一快照的 gauge：全零为 true，有非零为 false，gauge 缺失或读取失败为 null。
后两种情况即使已入账也不能声称正常排空；保持下线后重新采集或走上述未排空路径。

确认端点**不得用 runtime 的最大已接受 sequence、其他批次或当前 runtime 替代指定回执**。
例如 10 已入账而最终快照 11 尚未到达时，查询 11 必须是 `unknown`；11 已接收但未结算则为 `pending`。
若 11 已被后续批次取代，保持 `superseded`，运维重新采集最终快照并确认新回执。
完整回执、停止接入与排空证据随变更记录保存，关闭旧 runtime 时引用它们；无需新增编排状态机。

节点的 `drain_timeout` 只在收到停止信号后启动，且会话归零时可能提前退出，**不会等待主控确认**。
本流程因此在发停止信号前完成第 3 步，不能靠延长该超时制造“最终入账已确认”的保证。

### 3.1 窗口内暂停采集

证书轮换、隧道 reload、节点重启都会中断采集通道，按阶段区分：

- 下线、轮询会话归零与最终结算阶段继续采集，最终快照落库确认是停机门禁；
- 真正重建通道/进程期间暂停常规采集，在途普通请求失败后不盲目重放；
- 仅在**同一健康 runtime** 恢复时，用后续累计快照结算停采增量；
- runtime 已变且无最终入账证明时，旧尾账不可恢复，标记未闭合窗口并审计。

时间不确定范围按两次成功采集的实际间隔披露，不能用一个名义调度周期代替（R11）。
维护窗口也不豁免额度门禁：无新鲜健康结算时不刷新正额度，能连通则对全部受限身份收敛零额度；
请求结果不明则记 `unknown`；恢复后核对 runtime、收敛零额度，再用新健康结算重算，
不建立在途预留（D20）。恢复通道和确认零额度不等于缺口已经对账完成（README C33）。

### 3.2 告警吸收要有边界

窗口标记吸收该节点的采集失败类告警（采集失败、序号停滞、快照不可入账），
**但不吸收 P0 与控制面不一致类告警**。窗口结束后必须显式核对「开放告警为 0」才算收尾。

### 3.3 哪些变更必须走排空，不能走 SIGHUP

C20 允许「只改用户集合时优先 SIGHUP」，代价是在途连接被强杀。但有一类变更**连这个代价都不能付**：

**任何会增加计费身份总数的变更必须走排空五步。** 节点侧的身份计数包含 `active = false`
的 lineage（它们按 C9 永不删除），因此同一 runtime 内只增不减；一旦 SIGHUP 时越过
`max_identities`，节点会置位 `identity_limit_reached`，而**这一位是粘滞的**——
该 runtime 余下时间全部不可入账，唯一恢复手段是完整重启换 runtime（README C29）。

也就是说，一次填过头的 SIGHUP 不会给你一个错误返回，而是**静默地停掉这个节点的计费**，
直到有人发现并安排重启。账号池扩容（README D11）是最容易踩到这条的场景。

对照记住这组不对称：**启动时超限是失败关闭**（进程起不来，噪声大但安全），
**SIGHUP 超限是粘滞置位**（进程照跑，计费停了）。后者更危险，因为它看起来一切正常。

### 3.4 一次一台，并诚实命名

多节点轮换是**可接受中断的轮换，不是零中断轮换**——文档和 UI 都要这么写。
一次只轮换一台，冒烟通过后观察一段时间再切下一台。
实际顺序在变更单里批准，不在文档里预设。

## 4. 测试纪律

### 4.1 断言本身要被证明有效

**文本断言检查的是实现字符串，不是行为**，会因为无关原因「碰巧通过」。

> 生产教训：同类系统一轮清理里发现 6 处这类断言是错的或靠巧合通过——
> 其中一条声称测「争用回滚」，实际只是靠「两个目标各出现一次」凑够了出现次数。

→ **每条关键断言必须有反向测试证明它会红。** 注入错误，断言必须失败。
不能证明会红的断言，等于没有。

### 4.2 特权路径要在特权环境验证

> 生产教训：一个文件同步命令的选项顺序错误，让以 root 运行的接收端改写了整棵树的属主。
> **本机复现不到**——本地接收端不是 root，那个选项静默无效。

→ 故障矩阵要标注哪些用例**必须在 root / 真实节点上跑**，并在 CI 里区分这两类。

### 4.3 skip 不等于 pass

把「环境不支持」的跳过退出码当作失败。允许静默跳过，等于允许一整类用例悄悄消失。

### 4.4 措辞：自动化覆盖 ≠ 生产演练

同类系统明确把账号池耗尽、配置损坏、完整回滚、证书轮换标为「未实操」，
并写明「不为补齐勾选而破坏当前生产数据」。本项目沿用这个标准：
**把没跑过的演练写成已完成，比没写更危险。**

## 5. 门禁必须可执行

最后一条，也是最容易被当成套话的一条。

> 同类系统的 PKI 文档明确写着「该目录及其备份不得进入 Git」，
> 实际却有 118 个文件被跟踪，其中包括离线 root CA 私钥与发布签名私钥，
> 且没有任何 `.gitignore` 规则覆盖它们。

文档里的嘱咐不会阻止任何事。凡是「不得如何」的纪律，都要配一条**可执行的校验**：
`.gitignore` + 提交前脚本 + CI 门禁。本项目的脱敏门禁（README §11 的核对清单）同理——
它必须是一条能跑的命令，而不是一句提醒。
