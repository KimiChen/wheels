## 1. 目标与范围

`sing-box-plus` README §1 把「订阅生成、用户与额度管理、账单存储、管理后台、配置分发」整块
划给下游集成方，只留下 §5 的采集与结算契约和一份参考 collector。**本项目就是那个下游**。

**交付范围**，自下而上四层：

1. **节点通道**：`proxy-manager-agent`——节点侧只认预定义命令，经 mTLS 代理本机 UDS；
   快照与配额是两个权限档次不同的 socket，不许合并（C18）。
2. **采集与结算**：双 schema provider、六元组基线、幂等批次、周期账本、入账与基线的原子提交。
3. **控制**：周期配额判定、跨节点额度分配、`PUT /v3/quota` 下发与审计受控检索。**不做配置分发与排空编排**（D20）——节点变更由运维按手册执行，主控只在变更前后把账对上。
4. **接入面**：Web 控制台（`web-standard-kit`）+ 结构化 HTTP API + 飞书 / 企业微信
   （**只做两件事**：告警与日报推送、扫码登录与通讯录 RBAC）。

**明确不做（本轮）**：

- **IM 侧的任何写操作**：不做 ChatOps 命令、不做卡片审批、不做用户自助订阅。
  因此主控**不暴露任何 IM 事件回调端点**——飞书/企业微信方向只有「出站 API 调用」和
  「浏览器 OAuth 重定向」两类流量，没有平台主动打进来的 webhook。这是刻意收窄的攻击面，
  省掉了回调验签、重放去重、5 秒 ACK、卡片按钮越权这一整类问题。
- **限速**：节点侧只有「闸断」没有 shaping（`sing-box-plus` §4.9），要限速得改数据面。
- **多主控**：起步用 SQLite 单写者，与 `sing-box-manager` 同样的约束。HA 见 §10。
- **在节点上执行任意 shell**：agent 的命令集是封闭枚举，不接受模板化远端命令。
- **接管 `sing-box-manager` 的 SS 多跳编排**：两者共存，以 `node_id` 区分命名空间。

**验收定义**：在真实多节点环境下连续运行 7 天，节点侧长跑已验证的四项判据
（负增量 / 未知 runtime / 重复 sequence / unhealthy 入账）在主控账本上全部为 0；
对已持久化输入，任一事务中杀掉主控后恢复均不重复也不漏记；节点重启先恢复零额度，
批准与健康结算完成后在一个正常下发周期内恢复正额度。节点内存尾账丢失另按 R4 披露。

### 2.4 IM 侧（2026-09-17 核对）

- **企业微信自建应用必须配置「企业可信 IP」**，否则调接口报 `60020 not allow to access from your ip`；
  而要配可信 IP，得**先**设置可信域名或接收消息服务器 URL。这条直接绑死主控的**出口 IP**：
  主控换 IP、多出口或走动态 NAT 都会瞬间断掉通知。部署清单必须把出口 IP 当成配置项管理（§10 R5）。
- 企业微信网页授权 `snsapi_base` 是静默授权，只拿 `UserId`；`snsapi_privateinfo` 才拿头像等敏感信息。
  **本项目只用 `snsapi_base`**——主控不需要也不存这些敏感字段（§4.9）。
- 企业微信对主动调用有严苛频率限制，超速可能被判定为恶意刷屏并封接口权限。告警必须自带限频与合并（§4.10）。
- 飞书 `tenant_access_token` 有效期 2 小时，需集中缓存并提前刷新；`user_access_token` 走授权码换取。
- 两家的群机器人 webhook 都不需要应用凭据，因此作为**凭据失效时的降级通道**（§4.10）。

## 3. 术语

| 术语 | 含义 |
| --- | --- |
| 计费身份 / lineage | 节点侧的 `(inbound_tag, name)` 及其 `generation`，认证后的稳定归属单位 |
| 六元组 | `node_id + inbound.tag + inbound.generation + user.name + user.generation + runtime_id`，基线的完整键 |
| runtime 窗口 | 一个 `runtime_id` 的存活区间；跨窗口累计值清零 |
| 未闭合窗口 | 进程退出前没有「已排空 + 最终快照已入账」记录的 runtime 窗口，必须单独审计 |
| 批次 | 一次采集产出的增量集合，带幂等 ID，是入账的最小单位 |
| 额度池 | 一个用户在一个计费周期内的全局剩余字节，跨节点共享 |
| 分配额 | 池按权重切给某节点的 `remaining_bytes`，即 `PUT /v3/quota` 里的值 |
| 主体 | Web 控制台的操作者，来自飞书 / 企业微信 / break-glass 本地账号 |

## 4. 设计

### 4.1 组件与信任边界

   │   proxy-manager-agent                                      │
   │     ──UDS(只读)──► /v3/snapshot                            │
   │     ──UDS(只写)──► /v3/quota                               │

三条边界纪律：

1. **主控绝不直连节点的 UDS**，只经 agent；agent 绝不把 UDS 映射成公网监听（C18）。
2. **agent 不解析快照 JSON**。它按 `Content-Length` 字节透传，主控是唯一的解析点——
   多一个解析点就多一处可能把 u64 解成 double 的地方（C3）。
3. **agent 不缓存快照**（C18），也不聚合、不重排、不补齐。

### 4.2 `proxy-manager-agent`：节点侧的薄进程

二进制、systemd unit 与系统用户统一为 `proxy-manager-agent`，**名字刻意写全**：
它装在同时跑着 `sing-box-plus` / `shadowsocks-rust` / 转发链的节点上，
运维在 `systemctl` 或 `ps` 里必须一眼看出这个进程归谁。这与 C22
「退出码不是健康证据、要校验进程身份」是同一条口径——身份得先能被认出来。
下文在本节之后一律简称 **agent**。

**命令集是封闭枚举，共三条**，没有 `exec`、没有 shell 模板、没有任意文件路径：

| 命令 | 作用 | 危险度 |
| --- | --- | --- |
| `snapshot` | 打快照 socket，字节透传响应（含状态码与 `Content-Length`） | 只读 |
| `quota` | 仅 `plus_v3`：把主控给的 body 原样 `PUT` 到配额 socket，回传状态码与响应 | 改变转发行为 |
| `audit-list` | 仅 `plus_v3`：列出审计目录里**全部身份**的文件（活动的与已轮转的）及其大小。一次往返拿到全貌——逐身份问一轮是 301 次往返 | 数据主体明细 |
| `audit-read` | 仅 `plus_v3`：从给定字节偏移读一个审计文件。活动文件**只返回完整行**，已轮转文件原样返回；主控逐行校验完整身份与历史归属后才能返回用户（C35） | 数据主体明细 |

硬校验放在 agent 侧，因为它是唯一知道本机真实布局的一方：

- `audit-read` 的文件名形状校验、`canonicalize` 之后仍在 `audit_dir` 之内、以及
  「活动文件只返回完整行」这三条；agent 自身从不 `rm` 任何东西（C23）；
- `snapshot` 单飞：同一节点同一时刻只允许一条 in-flight 采集，第二条直接本地 429，
  不去撞节点的并发上限（C7 的 429 是「可重试且不得入账」，本地挡掉能减少这类可重试事件）。

**mTLS 与授信**：双 CA（控制面 CA 签主控客户端证书，节点 CA 签 agent 服务端证书），
SPKI 指纹带外核对后授信，支持吊销——与 `sing-box-manager` 的 enrollment 模型同构，
**不复用它的实现**（D1），但威胁模型照抄：agent 被动、不主动回连、不接受管理员提供的任意远端命令。

三条 PKI 纪律，都来自同类系统的生产教训（细节见 [`docs/threat-model.md`](docs/threat-model.md)）：

1. **在线信任的是精确 leaf，不是 intermediate。** 授权 bundle 里放的是那一张经离线 SAN/EKU
   校验过的 client leaf 本身；即使由同一个 intermediate 新签一张，也不该通过握手。
   要诚实地写明这实现的是**运行时精确证书授权**，不是运行时逐字符串比较 SAN。
2. **吊销的实质是从授权 bundle 移除旧 leaf。** 证书上的 `REVOKED` 标记只是离线审计记录，
   不会让任何在线组件拒绝谁。流程固定为 `overlap → 换叶 → revoke` 三阶段，
   reload 顺序**先节点后主控**——反过来会在切换窗口里把自己关在门外。
3. **私钥不离开所属节点**，root 与全部 intermediate 私钥留在离线 workspace。
   证书到期巡检只读公钥叶子，**不得为了巡检把采集身份加进持有私钥的组**（那等于抹掉 C18）。
   而且这条纪律必须做成**可执行的门禁**（`.gitignore` + 提交前校验），不是文档里的一句嘱咐——
   同类系统正是在这里栽过：README 写明「密钥不得进 Git」，实际 CA 私钥已被跟踪。

**应用层 HMAC（D12）**：传输层 mTLS **只提供通道**，不能替代每节点独立的应用层签名。
每节点一把独立 HMAC key（32 随机字节，不得复用任何 CA、发布签名密钥或数据面 PSK），
签名覆盖 canonical 请求与响应，带 nonce 重放缓存与时间戳偏差窗口。
收益很具体：若将来在节点侧插入 C18 允许的那种反代，mTLS 会在反代处终结，
那时**只有应用层 HMAC 还能证明「这份快照来自这个节点」**。
参考实现见 `shadowsocks-rust-plus/patches/0003-user-audit.patch` 中的
`crates/shadowsocks-auditd/src/export.rs`（需按节点 README 准备源码）。

**权限**：agent 与 `sing-box-plus` 同机不同 uid。快照 socket 给 agent 只读组权限，
配额 socket 给 agent 写权限——这两档权限不同，配到同一个组上等于抹掉 C18 想保住的分界线。
落地形态见 C28：agent 需要**主组 + 补充组**才能同时穿过两档权限，缺一即启动失败。
可直接参照 `shadowsocks-rust-plus/packaging/*.sysusers` 与 `*.tmpfiles`
（`0751` 父目录 + `0750` 分组隔离子目录，注释写明了为什么 `0750` 父目录会破坏穿越）。

**NAT 后的节点**本轮不支持（主控主动连）。若将来需要，走反向隧道而不是让 agent 主动推数据——
推模式会把「谁是真相源」这件事翻过来，结算方向的幂等假设要整套重做。

**拉模式的补偿边界。** 同类设计（`shadowsocks-rust-plus/docs/CONTROL_PLANE_USAGE_STATISTICS.md` §3）
推荐的是节点主动上报 + 本地 outbox 暂存，靠「主控确认持久化后才清理本地记录」扛断网。
本项目选了拉模式，于是自然要回答：**主控不可用的那段时间，快照去哪了？**

只有在**同一 runtime 持续存活、计数器健康且 lineage 完整**时，恢复后的快照才能带回停采期间的累计增量。
增量整体归到恢复时的桶，时间不确定范围是两次成功采集的实际间隔，可能远大于调度周期。

若停采期间节点重启或崩溃，旧 runtime 未落库的尾账无法从新计数器恢复，必须标记 `unclosed` 与
计量缺口（R4），不能声称只损失时间精度。本轮接受这项残余风险，不提供节点持久计量保证。
若业务要求跨崩溃不丢字节或精确时段计费，需要另行设计节点侧持久计量/事件时间；
仅缓存已拉取快照的 outbox 也救不回两次快照之间尚未持久化的尾账。

### 4.3 采集：快照校验与归一化

采集层只负责四件事：取原始字节 → 逐字段校验 → 归一化成统一 lineage 增量 → 交给账本。

**只对接 `sing-box-plus`（D3）**：`GET /v3/snapshot`，`schema_version` 必须为 `3`。

| 项 | 值 |
| --- | --- |
| 路径 | `GET /v3/snapshot` |
| `schema_version` | 必须 `3`（以节点侧 Go 常量为准，见 §2.1 旁注） |
| `health` 闭集 | **恰好四位**：`counter_overflow` / `sequence_overflow` / `identity_limit_reached` / `audit_dropped` |
| session gauge | per-inbound 的 `tcp_sessions` / `udp_sessions` |

**路径与版本号必须成对硬校验**：读到 `1` 或 `2` 一律整份拒绝并告警，不接受「看起来能跑」的
半兼容（C10）。节点已经写明 `/v1` 与 `/v2` 恒为 404——主控这一侧再加一道，
是因为主控可能被指到一个根本不是 `sing-box-plus` 的端点，那时 404 不会出现。

> **早先版本支持 `shadowsocks-rust-plus`（`srp_v1`）作为第二个 provider，本轮去掉（D3）。**
> `sing-box-plus` 在协议、计量与配额三个维度都是它的超集：多支持 VLESS，
> 多 `identity_limit_reached` / `audit_dropped` 两位 health，多 session gauge，
> 还多一整条 `PUT /v3/quota` 闸断链路；两边的 SS2022 都固定在
> `2022-blake3-aes-*-gcm` + EIH，凭据格式兼容。
>
> **唯一不是超集的是审计**：`srp` 有独立 auditd + 本机 durable spool + HMAC 导出，
> 而 `sing-box-plus` 只有按 `max_bytes` 轮转的 JSONL 文件——低流量身份可能数天拿不到归档
> （§4.8 已明确接受这个限制）。去掉 `srp_v1` 是拿这一点换掉整条双 provider 的不对称建模。

归一化后的内表字段名**不必与 wire 同名**：键的语义由六元组确定，而非由字段拼写确定（plus §5.1）。
这条允许内表用更适合查询的列名。

**解析纪律**：wire 上的 u64 用 Rust `u64` 精确解析；多方向、多节点及长期累计用 checked `u128`。
SQLite 的无损文本编码与禁止隐式数值转换规则见 `docs/data-model.md` §3.1；
出到 HTTP API 与前端时一律转**十进制字符串**（§4.11）。

### 4.4 账本：入账与基线在同一个事务里

节点 README §5.1 把「推进基线」与「产出计费记录」的先后定成一次**显式取舍**：
先产出记录后推进基线 = 崩溃即重复计费；反过来 = 崩溃即漏记一批。参考 collector 选了后者
（宁可漏记不可重复），并写明「要两者都不发生就需要把两步做成一次原子提交」。

**主控有事务型存储，所以把两步做成一次提交**——这是本项目相对参考实现的实质增量。
完整的 11 步顺序与表结构见 [`docs/data-model.md`](docs/data-model.md)，骨架是：

```text
BEGIN IMMEDIATE                                    -- 经单写者队列取得 SQLite 写事务
  SELECT ... FROM node_runtimes WHERE ...            -- SQLite 不使用行级 FOR UPDATE
  -- 不按外部传入的 batch ID 结算：持锁后按 (runtime_id, status, sequence)
  -- 选最小的未处理 sequence；更旧且未处理的标 superseded
  INSERT INTO snapshot_batch(...)                    -- 唯一索引挡重放
  INSERT INTO snapshot_payload(...)                  -- 压缩原文，是结算输入而非审计附件
  -- 全快照先在内存里校验通过，再落任何一行 delta
  INSERT INTO usage_ledger(...)                      -- 只追加的计费记录（仅非零增量）
  UPDATE usage_lifetime_totals ...                    -- Rust checked u128 累加后绑定文本
  UPDATE usage_cycle_totals ...                       -- 与账本、游标同一事务
  UPDATE counter_cursor SET ... WHERE (六元组)        -- 推进基线：零增量与 active=false 也要更新
  UPSERT rollup_job(hour_bucket) SET version = version + 1, status = 'pending'
COMMIT
```

- **幂等批次 ID** = 对 `node_id` / `runtime_id` / 完整 lineage / `sequence` / 四向增量做**长度明确的
  canonical 编码**后取 SHA-256——不用字符串拼接，那会产生分隔符歧义。唯一索引冲突即整批丢弃。
  注意批次 ID 挡不住「先产出后推进」的重放（重放出来的 `sequence` 与增量都不同），
  所以它是第二道，不是第一道——第一道是上面那个事务。账本幂等另由
  `UNIQUE(batch_id, runtime_identity_id)` 兜底，**不能依赖「通常不会重复」**。
- **原始快照字节必须先原子落盘，并且是结算输入，不是审计附件。** 异步结算要能**从库里恢复
  完整快照**；C5 的失败关闭要人工介入，没有原始字节无法复盘；C3 的 u64 解析争议也无从佐证。
  清理任务必须联表确认批次已处于终态并超过宽限期，**不得仅按过期时间删除仍未结算的输入**。
- **不持久化中间 `processing` 状态**：检查 runtime 与 batch 在同一写事务里，崩溃整笔回滚，
  批次自然保持可重试。
- **禁止 `INSERT OR REPLACE`**：它是删除后插入，会破坏审计与引用语义。
- **按 `runtime_identity_id` 排序读游标**，保证处理与哈希顺序确定；串行性由 SQLite 写事务保证。
- **首快照策略** per-node 显式配置 `baseline | include`，**配置缺省即启动失败**（C8）。
  更强的一层是 **runtime 批准登记**：每个 runtime 显式登记并留存策略、原因与操作者；
  未登记的 runtime（含影子 runtime）不得进入批准文件，其上的身份不可分配（见 D11）。
- **`active=false` 的 lineage 继续保留基线**，只在 UI 上标灰（C9）；
  **已观察过的 lineage 无故消失则整份拒绝**（C25）。
- **身份建模约束（D17）**：同一业务用户在同一节点上**只有一个计费身份**。
  可替代的流量（不同设备）走同一个身份；只有**计费口径不同**时才分开，
  而那时它们应当各自独立成池，不共享额度（§4.5）。这条写在账本这一节而不是分配那一节，
  是因为它是**建模决定**：一旦身份建多了，下游的分配、不变量与测试都要跟着多一层。
- **同一个名字挂在多条协议入口上不是「多身份」**（2026-09-20）。`user0001` 的 SS 与
  VLESS 是同一个人的两种到达方式：槽位键是 `(node_id, identity_name)`，一个名字
  一个节点**只有一行** `identity_routes`；`bump_cycle` 按 user_id 汇总，两个协议的字节
  进同一行 `usage_cycle_totals`。节点侧确实是两个互不相干的 `quotaCell`
  （挂在 `(inbound_tag, name)` 上），所以额度对它们**各发全额**而不是平分——
  代价与 D24 同源，见 D17 修订条。
- **拒绝分两类，按「不可用的是谁」分。** 混成一类会丢数据：
  - **终态拒绝**——**快照本身**不可用：计数器倒退、不可入账的 `health` 位、
    已观察的 lineage 消失、`sequence` ≤ 已接受值、整份解析失败。重试多少次都一样，
    批次就该烧掉。
  - **暂不结算**——**主控侧**前置条件没满足：runtime 未登记、已登记未批准。
    快照是好的，**批次必须保持 `pending`**。
    这不是洁癖：`runtime_id` 与 `started_at_unix_ms` **就在快照里**，
    运维根本不可能在看到第一份快照之前批准一个 runtime。
    「先收到、后批准」是正常流程，把它判成终态等于**让每个新 runtime 的首快照必然丢失一份**。
- **拒绝入账的分支不推进任何状态**：`health` 的不可入账位、`schema_version` 不符、
  `Content-Length` 不符、JSON 截断、429、连接重置，一律不进事务（C4 C7）。
  但只要 envelope 还能识别出 node/runtime/sequence，**可审计的拒绝也要留一条批次回执**
  （状态 `rejected`，绝不推进 sequence 与游标）；完全无法识别的畸形请求只进限量安全日志。
- **`audit_dropped` 单独走告警路径**，`usage` 照常入账（C4）——把审计丢弃算进入账判据，
  等于让磁盘写满连带停掉计费，这是节点侧刻意不做的，主控也不要做回来。
  该位只有 `plus_v3` 有。

### 4.5 周期、额度池与跨节点分配

**额度与周期都是全局的（D21）**：所有人同一个月度额度、同一个自然月周期，在设置里配一个值。
没有 per-user 套餐，也就没有周期锚点、折算系数与套餐变更迁移这一整套。
**改额度对本周期立即生效。** 额度是参数，账本记的是用量；
`剩余 = 额度 − 本周期已用` 本来就该跟着重算。两个方向都是期望行为：

| 改动 | 对已用 320 GiB 的人 | 说明 |
| --- | --- | --- |
| 300 → 500 GiB | 从「已用尽」变成「剩余 180 GiB」 | **本来就该让他继续用**——这正是调高额度的目的 |
| 300 → 100 GiB | 仍为「已用尽」，下发零额度 | 其他已用超过 100 GiB 的人也会被闸断，见下 |

三条配套要求：

- **改完立即触发采集、结算与下发**，不等下一个定时周期。额度设置、revision、审计与待下发任务
  在同一写事务提交；各节点任务进入现有单飞队列，主动取得上次正额度请求之后的新健康快照，
  结算后按最新 revision 重算全部受限用户，再以新 epoch 下发完整表。已占用或过期的 sequence 不得复用。
  发送前再次检查额度 revision 与预算版本，过时任务重新计算，不得把旧配置的余额推回节点。
- **调低必须先预览再确认**：显示按当前已结算用量预计将被闸断的名单及用量核验时刻。
  后续真实流量仍可能增加用尽人数。调高不需要预览。
- **改额度落审计**：谁、何时、从多少改到多少。这是一次影响全体的操作。

“本周期立即生效”指主控立即采用新参数并启动上述流程，**不表示节点已确认收到新表**。
实际提交的 `PUT /settings/quota` 返回 `202`、新 revision、受影响人数与下发状态；`GET` 返回当前 revision 的逐节点结果。
`dry_run=true` 只返回预览，不改设置、不写下发任务；调用方展示结果时须核对 revision，不能把旧结果用于新设置。
节点状态区分 `pending` / `applied` / `safe_zero` / `unknown` / `failed`：只有按新配置计算的完整表收到 200
才是 `applied`。采集失败或不健康时按 C33 尝试完整零表，确认成功记 `safe_zero`；结果不明记 `unknown`。
只要还有节点未应用新配置，UI 就显示“已保存，节点待生效”及原因，后台重试；不能显示“全部已生效”。

一个不会自动发生的事要说清楚：**调高额度不会让已经断掉的连接自己回来**。
节点侧只是重新允许新连接，用户需要自己重连。UI 上要写明，否则会被当成没生效。

周期切换时**只重置主控自己的周期起点基线**，不碰节点上的累计值（C1 C2）。

**池**：`remaining_pool = 全局月度额度 − Σ(本周期起点以来各节点的增量)`。
绝对值一次都不参与比较（C11）。

**三个口径并存，不要混用**（表结构见 `docs/data-model.md`）：

| 口径 | 含义 | 用在哪 |
| --- | --- | --- |
| 本次增量 | 一个批次结算出的四向 delta | 账本行、小时/日汇总 |
| 周期累计 | 本计费周期起点以来的和 | 配额判定、额度池 |
| 永久累计（lifetime） | 跨周期、跨 runtime 的总和 | 用户总览与长期报表，**不用来比较周期配额** |

订阅头使用与 `total` 对应的周期累计（§4.7）。永久累计单独持久化于 `usage_lifetime_totals`，
与账本和游标原子更新，不能在清理旧账本后改为对剩余明细求和（`docs/data-model.md` §9）。

**同一节点上的多个计费身份：先想办法让这个问题不存在（D17）。**

1. **一个人一个节点一个身份。** 「不同设备」这类流量完全可替代的情形**不应该建多个身份**——
   建了就凭空多出一层分配问题，而且它的抖动尺度比节点间更细。这是一条**身份建模约束**（§4.4），
   不是分配层的参数。由 `idx_identity_routes_active_per_user` 在数据层硬守着。
   **注意「多条协议入口」不在此列**（2026-09-20）：同一个名字的 SS 与 VLESS 入口
   共用一个槽位、共用一份归属、字节直接相加，它们从来没有进入过这个分配问题——
   额度对它们镜像下发、**各发全额**（D17 修订条、D24）。
2. **口径不同则独立成池。** 只有当两个身份的**计费口径不同**才必须分开
   （C17：按方向计费要在主控折算，不同口径的折算系数可能不同）。但那时它们的字节
   **不可直接相加**，`Σ 身份限额 = 节点分配额` 这条不变量本身就不成立——
   正确做法是**各自独立的池**，而不是共享一个池再切。
3. **剩下的边缘情况**（同口径、因历史原因分了身份）：把下面的乘法更新**递归应用**到身份级，
   **身份级不设地板**。地板的存在理由是「用户漫游到冷节点别被立刻闸断」，
   而同一节点内的身份切换不是用户的自主行为。

**只有情形 3 下**，`Σ(同节点各身份限额) = 该用户在该节点的分配额` 才是有效不变量；
情形 2 下断言它反而会掩盖「两个口径被错误地相加了」这个真问题。

**分配对象与预算。** 一个用户可在多个 `plus_v3` 节点上有身份。先按用户/计费池计算目标，
再按节点合并全部用户，形成一次全量请求。

```text
B = u64::try_from((quota as u128).saturating_sub(cycle_used_u128))  # 本轮可分配预算
N = 本轮可更新的节点数
```

`N = 0` 或 `B = 0` 时不产生正额度。饱和减法保证 `used > quota` 时 `B = 0` 而不是下溢（C32）。

> **这里曾经有一层在途授信预留（原 C34）。** 它解决的是：下发结果不明时，
> 旧授权可能仍在节点上生效，而主控又把同一批字节分给了别的节点 → 实际授信总量超过池。
> 本轮按 D20 去掉了这一层——配额是内部限额，几 GiB 的超发不构成问题，
> 而预留带来的冻结、核销、`H > pool` 对账是一整套没有对应收益的机制。
> **代价写在 §10 R2**：超发不再有有限上界。这条取舍的前提是「配额不对应真实计费」，
> 前提变了要重估的是这条决策本身，不是补一个局部修复。

#### 权重、地板与冷节点恢复

**消耗率只用于估计需求，不作为“已闸断”的证据。** 记上一轮确认下发的额度为 `a_i`，
相应观察窗口内的已结算增量为 `u_i`。节点在 I/O 完成后才扣额，且快照与下发时刻不重合，
所以 `u_i / a_i` 可以大于 1；恰好等于 1 也不能证明触发了闸断。

只有下发结果明确、窗口没有跨越多个补额 epoch 的样本才更新权重；否则沿用上一权重。
`a_i = 0` 时不做除法，走探测分配。保留原始消耗率用于诊断，只在权重函数内截到 `[0,1]`。

采用持久化的正整数需求权重 `w_i`，不再把可能为零的 `a_i` 本身当作权重：

```text
初始 w_i = 1024；范围 [1, 2^31 - 1]
若样本可用且 a_i > 0：
  w_i = clamp(floor(w_i × (a_i + 3 × min(u_i, a_i)) / (2 × a_i)), 1, 2^31 - 1)
否则保持 w_i
```

所有乘加使用 checked u128 中间值。这是 `f(r) = (1 + 3r) / 2` 的整数实现，
只作为初始参数；响应速度需由 M2 的流量分布测试验证，不宣称任意参数下都在固定轮次收敛。

**先保留基础额度，再分剩余预算，最后不再归一化基础额度。**
`floor` 默认 64 MiB；`probe_bytes` 默认 1 MiB，均可配且须满足 `1 ≤ probe_bytes ≤ floor ≤ i64::MAX`。

```text
若 B >= N × floor：
  base_i = floor
否则若 B >= N：
  base_i = min(probe_bytes, floor(B / N))
  标记“地板已失效”
否则（0 < B < N）：
  按持久化轮转游标给 B 个节点各 1 字节，其余为 0
  标记“地板已失效”；下一次成功收敛后推进游标

extra = B - Σ base_i
share_i = floor(extra × w_i / Σ w_j)
余数按乘除余数从大到小补 1，平局按 node_id 字节序
alloc_i = min(base_i + share_i + 余数分配, i64::MAX)
```

`N × floor`、权重之和、比例乘法均 checked；达到 wire 上限后剩余预算留在池中，不能溢出回绕。
正常计划满足 `Σ alloc_i ≤ pool`；当地板可用时同时满足每个可更新节点 `alloc_i ≥ floor`。
例如旧分配 `[64,336] MiB`、用量 `[0,100] MiB`、剩余 300 MiB，必须先保留两个 64 MiB，
再按权重分 172 MiB；不能先抬高权重再整体缩放，产生 `[54,246] MiB` 这样的地板违例。

探测额度和权重下限使零额度节点不再成为吸收态。`B >= N` 时每个可更新节点至少有 1 字节；
`B < N` 时只能轮转探测，不能同时给所有节点正额度。只有预算持续可用且下发成功，轮转才有进展；
1 字节探测也不代表可维持业务吞吐，节点事后闸断仍存在分块超额。
**不承诺「提频到 10s 就在一轮内恢复」**：预算、节点数和下发失败都会影响恢复时间。

同节点同口径多身份（D17 情形 3）复用正权重与探测规则，但不设 64 MiB 地板；
身份额度之和等于节点分配额，整数余数分配规则保持一致。不同口径的池各自计算。

**这一段自 2026-09-20 起没有在线调用方。** 唯一会产生「同节点多条身份记录」的情形
是一个名字挂在多条协议入口上，而那按 D17 修订条**不走切分、各发全额**。
`split_identities` 与它的用例完整保留但不接线——与 D24 对 `allocate`/`weight`
的处置一致。要把它接回来，改的是 `quota::table::assemble` 里的那一个循环。

#### 下发纪律

1. 主控在单写者事务里持久化完整节点请求、body 摘要与新 epoch，**再发请求**。
   每节点额度命令单飞；单用户手动重算也进入同一调度队列，不能绕开它直接 PUT。
2. 全量表会重设其中每个用户的余额。因此每次发送必须重算表中**所有受限用户**，
   不能把「其他用户上次下发的值」原样复制回去——那会反复补回已经消耗掉的额度。
3. 每个含正额度的请求必须绑定该节点**上次正额度请求之后重新采集并结算**的 sequence；
   同一 sequence 最多支撑一份正额度完整表，这项占用与请求一起持久化，手动重算也不例外。
   发送前检查 `snapshot_max_age`（默认目标采集周期的两倍，可配）；队列等待造成过期则重新采集重算。
   手动重算或额度变更遇到 sequence 已占用时，主动排队采集新快照，不等待下一个定时周期。
   仅「快照还没过 TTL」不足以授权反复刷新同一份余额；纯零额度安全表可重复收敛。
4. 超时、连接重置、主控在发送后崩溃时**结果不明**。恢复后先核对 runtime，
   再以更高 epoch 的表收敛。**本项目不为这段不确定性记账**（D20）：
   下一轮正常重算即可，代价是那一轮可能存在重复授信——见 §10 R2。

#### 超发说明与自适应频率

**没有有限的超发上界，这是 D20 的直接代价。** 去掉在途授信预留之后，
下发结果不明的那一轮里，旧授权可能仍在节点上生效，而主控已经按新的计划分配了同一批字节。
超发幅度取决于失败前那笔授权的大小，**没有上界可以对外声明**。

即便忽略这一项，另外两个来源也只在很强的前提下才有界：

```text
采集与下发间隙 ≤ Σᵢ(峰值速率上限ᵢ × (成功采集间隔上限ᵢ + 下发收敛延迟上限ᵢ))
节点事后闸断   ≤ Σᵢ(节点并发传输的闸断分块超额上限ᵢ)
```

前提是峰值速率与分块超额都有可靠上限。实测平均速率、默认 60s 周期或一次 PUT 成功，
都不能单独证明这些前提。

**因此 API/UI 一律不展示「超发上界」这个数**——配额是内部限额（D20），
产品说明里写的是「可能超发，幅度取决于下发失败时的授权额」，
而不是一个看起来有保证、实际不成立的数字。

| 提频触发 | 判据 | 处置 |
| --- | --- | --- |
| 池将尽 | 按有效样本速率估计的剩余时间低于配置倍数的采集周期 | 缩短观察间隔，不按单一剩余百分比推断风险 |
| 需求偏高 | 有效样本 `a_i > 0` 且 `u_i / a_i ≥ 0.9`，包括大于 1 的情形 | 标记“可能额度受限”，提频复核；不称作已证实闸断 |
| 冷节点探测 | 存在零额度且有可重新分配预算的节点 | 推进探测分配 |

目标周期默认 60s → 10s；单飞、退避与全网提频预算优先，API 显示实际采集间隔。
提频不允许在无新健康账本时刷新正额度。

#### 全量清单与故障处置（C30、C33）

`Limited(0)` 必须下发，`Unlimited` 必须省略；内部使用
`Quota::Unlimited | Quota::Limited(u64)`，不用 `0`、`None` 或 `u64::MAX` 充当无限额度哨兵。

- 每个请求的身份集合必须等于**节点上所有受限用户的全部当前有效身份**，逐项唯一且保留零值。
  inactive lineage 的计费游标仍保留，但已不在节点当前配置中的身份不能继续放进写清单（C15）。
- 某用户 `pool = 0` 时将其全部身份置零，其他受限用户仍按当前预算在同一张表中列出。
  两个不同用户同时重算、一个无限额度用户与一个零额度用户共存，都是必测场景。
- 节点快照不健康、回退或超过新鲜度窗口时，禁止正额度刷新；控制通道可用就下发完整节点表，
  将**该节点全部受限身份置零**。控制通道不可用时告警，并在恢复后先收敛零额度。
- 受限节点启用 `startup_action=deny`，并配置明确的 `stale_after` / `stale_action=deny`。
  后者仅阻止过期后的新连接，不能替代已有连接的额度回收；停推本身不会将已下发的限额变为无限。
- 新 runtime 未批准、首快照未结算或旧窗口缺口未处理时，只做零额度安全收敛。
  只有批准、健康和预算门禁全部通过后才恢复正额度。

**下发状态机**：先入账 → 计算所有受限用户预算 → 持久化请求与 epoch → 推送 → 记录结果。

| 响应 | 含义 | 动作 |
| --- | --- | --- |
| 200 | 本请求已生效 | 记录 `applied`；epoch 在发送前已经占用 |
| 409 | node/runtime 不符或 epoch 未前进，错误体不区分 | 核对节点身份、取快照核对 runtime；按下述流程安全收敛 |
| 400 未知身份 | 配置与全量清单不一致，请求未应用 | P1 告警，核对当前配置与有效身份后重建整表 |
| 已确认未执行的 429 | 可重试 | 退避后重新核验账本与预算；不能机械地刷新旧正额度 |
| 超时 / 连接重置 / 无可信响应 | 是否应用未知 | 记 `unknown`；恢复流程先核对 runtime 再收敛零额度 |

**只有 429 算「已确认未执行」。** 采集路径上「连不上本机 UDS」是可重试的——
一次失败的 `GET` 没有副作用；配额路径上不成立：`PUT` **可能已经被节点应用了**，
只是响应丢了。把它当成可重试，恢复流程就会重发同一个 epoch 并稳定撞 409。
两条路径的判据必须不对称，因为一边的失败没有副作用、另一边有。

409 后不从响应体猜原因：

1. 校验连接目标和 `node_id`，不一致先停止推送并告警；
2. `runtime_id` 已变：旧窗口按闭合证据对账，新 runtime 登记批准；立即下发零额度安全表，
   新 runtime 的 epoch 可从 1 开始，健康结算与预算门禁通过后再发正额度；
3. runtime 相同：从**发送前持久化的最大已分配 epoch** 取更大值，不依赖最后一次 200。
   响应丢失不能证明旧请求没执行；连续冲突需排查其他写入者并升 P1。

**接管一个 live runtime 时无法发现节点当前的 `epoch`。** 409 的错误体不带它
（`quota_endpoint.go` 两条分支都只回 `{"schema_version":3,"error":{"code":409}}`），
节点也没有「读回当前 epoch」的端点。上面第 3 步靠的是**主控自己持久化的最大已分配值**，
可它只在「主控崩溃后恢复」时成立；换一个前提——本项目首次接管一个已经被别的采集器
管着的 runtime，或者主控的库丢了——那个值根本不存在。

两条出路，优先前者：

1. **换 runtime**：按节点侧 §5.3 走排空五步重启，新 runtime 的 `epoch` 从 1 开始，
   干净且不需要猜。代价是一个停机窗口。
2. **用全零安全表指数探测**：`epoch = 1, 2, 4, 8, …` 直到拿到 200。每次要么 409
   （整份丢弃，无副作用），要么 200（应用了一张全零表——而无新鲜健康结算时下发
   全零完整表本来就是 C33 要求的肯定动作，所以这条探测路径上的每一步都是安全的）。
   探到之后按 §4.5 的纪律继续。**不得**用正额度表做这种探测。

`epoch` 是 per-`(node_id, runtime_id)` 的持久化 u64，必须 ≥ 1；耗尽时失败关闭，不回绕。
`remaining_bytes` 在 wire 上是非负 int64，序列化显式检查范围；聚合累计与数据库编码见
`docs/data-model.md` §3.1。健康状态不能靠静默截断或跳过零值条目维持。

### 4.6 节点变更：不由主控编排（D20）

**控制台不做配置分发、不做排空编排、不做回滚。** 节点配置变更、版本升级与重启
由运维在节点上按手册执行，主控只负责在变更前后把账对上。

去掉的理由和 §4.5 去掉预留是同一条：这是小众产品、单人管理（D19），
一个人在一台机器上按步骤操作，比主控远程编排一套七态状态机要可靠得多——
而且编排本身会引入「主控以为节点处于什么状态」与「节点实际处于什么状态」的第二处不一致，
那正是这个项目在结算侧花了最大力气消除的东西。

**但 C19 的排空五步不因此消失，它变成运维手册里的必须步骤**，
完整流程与每步的判据见 [`docs/operations.md`](docs/operations.md)：

1. 停止接入新连接（固定的下线/防火墙钩子，不是先发停止信号）；
2. 轮询快照的 `tcp_sessions` / `udp_sessions` 至 0 或超时——
   **这是 `tcp_sessions` / `udp_sessions` 唯一的用途**（C6）。
   gauge 不可用时（读取失败、字段缺失）只能按固定超时，**该窗口无条件标记未排空**；
3. 通过采集端点取得最终快照的 `runtime_id / sequence / payload_sha256` 回执，再用只读确认端点
   查询**这份快照**是否已持久化入账。成功采集不等于入账完成，较早或较晚快照的成功也不能代替该回执；
4. 停进程、换配置、起新进程（新 `runtime_id`）；
5. 在主控登记新 runtime 与首快照策略，**先恢复零额度安全表**，
   健康结算通过后才恢复正额度（C33）。

**主控只参与两类操作**：第 3 步的采集与精确入账确认，和第 5 步的 runtime 登记。
采集复用既有端点，确认只读；完整回执与排空证据随变更记录保存，不引入远程编排状态机。

**账号池扩容同样走这条路**（D11、C29）：增加身份数必须重启，不能 SIGHUP——
SIGHUP 越界会置位粘滞的 `identity_limit_reached`，让该 runtime 余下时间全部不可入账。

**未闭合窗口仍然会发生**（崩溃 / OOM / 断电），它不依赖编排。
异常退出留下的窗口单独归类、进告警，不得当作正常周期切换（§4.10）。

#### 账号池预分配（D11）

节点配置里**预生成一批计费身份**，新用户首次登录时在事务内 **FIFO 唯一分配**一个，
分配关系落主控库。这样新用户上线**完全不触碰节点配置**：不渲染、不 `check`、不 SIGHUP、
不重启，也就不触发 C20 的在途连接强杀。

- 身份**只有在全部已批准 runtime 上都观察到、且四向计数全为零之后**才可分配。
  这比 C8 的 `baseline | include` 二选一更强：它用「实际观察到零基线」代替「相信配置」。
- 影子 / 未批准 runtime 上的观察不算数，也不得进入批准文件。
- **池耗尽是必测路径**：同类系统把它列为「未实操」项，本项目要在 §8 里补上用例，
  包括耗尽时的告警、水位阈值和扩容发布流程。

**代价不是「占掉一点身份上限」，而是一条会停掉整节点计费的路径**（C29）。
节点侧 `max_identities` 的对账逻辑有两个性质，叠加起来很尖锐：

1. **计数只增不减。** 身份总数把 `active = false` 的 lineage 一起算进去，
   而 C9 / C2 要求这些 lineage 永不删除——所以同一个 runtime 内，这个数**只会往上走**。
   池子的余量必须按「runtime 生命周期内累积的残留」估，不是按「当前活跃数」估。
2. **越界的后果分两种，而 SIGHUP 那种最糟。** 启动时超限直接报错、进程起不来（失败关闭，
   噪声大但安全）；**SIGHUP 重载时超限则置位 `identity_limit_reached`，而这一位是粘滞的**——
   置位后该 runtime 余下时间**全部不可入账**，唯一恢复手段是完整重启换一个 runtime。

因此两条硬规则：

- **池扩容必须走排空五步，不能走 SIGHUP。** 这不削弱 D11 的本意：D11 要省掉的是
  「每来一个新用户就动一次节点配置」，而扩容是低频事件，走完整流程本来就合理。
- **池容量与 `max_identities` 的余量是一个必须显式配置并告警的比值**，
  不能等撞上了再说——撞上的那一刻已经停止计费了。

#### 发布器纪律

细节见 [`docs/operations.md`](docs/operations.md)，四条底线：

- **dry-run 默认、`--apply` 显式**；固定精确 HEAD、构建不可变快照；网络只传到特权私有 stage；
  持锁后才把 stage 增量同步到活动目录。
- **中断恢复 marker**：记录命令、commit、原始备份、目标 before/after 摘要。中断后只允许用
  **相同命令 + 相同 commit** 复用原始备份向前收敛，全部健康检查通过并刷盘后才删 marker。
  **不得手工删 marker，也不得清理它引用的备份。**
- **回滚必须整组恢复**（配置 + 数据 + 指针），不能只切一个指针。
- ~~**数据库迁移不得与应用发布绑定**，分两轮执行。~~ **本项目没有迁移**（D22），这条不适用。
  但它背后的教训仍然成立，只是换了落点：生产教训是绑在一起时，发布顺带引入的无关改动
  让健康检查失败，门禁把**已经成功的迁移一并回滚**了。同一形状在本项目是——
  **建库与发布回滚不得共用一个门禁**：库已经建好之后，发布失败不得连带删库。

### 4.7 订阅

- token 只存哈希，**明文只在创建时显示一次**；首次登录时在事务内创建，之后**只读**。
- 输出 `ss://` / `vless://` raw、Clash/mihomo YAML、sing-box 客户端配置；二维码在浏览器本地渲染。
- 订阅端点与管理端点**分开监听、分开限流**；订阅端点不带会话 cookie，只认 token。
- 本轮 IM 不做自助，**订阅链接只在 Web 控制台内出现**，不进任何 IM 消息——群里发一次订阅链接
  等于把它交给整个群的聊天记录和每个人的设备。

**轮换是运维动作，不是用户自助动作。** 同类系统上线后把自助轮换**整个删掉**
（删路由、删控制器、删仓储方法，不是 CSS 隐藏入口），只保留吊销字段给后台应急。
理由很实在：轮换会让该用户所有已导入的客户端**静默失效**，而用户通常不知道要重新导入。
本项目沿用这个结论——吊销是运维动作，**走命令行**（控制台不再有订阅管理页，D20），
需二次确认并落审计；自助轮换不做。

**三个客户端必需的响应细节**（缺一个都会在真实客户端上出问题）：

- **`Subscription-Userinfo` 响应头**：Clash / mihomo 靠它显示流量与到期。
  `upload` / `download` 用**当前计费周期已结算累计**的十进制字节，
  `total` 用**同一周期、同一计费口径的真实配额**、`expire` 用周期结束时刻。
  若按方向折算，两项用与配额一致的折算值并在订阅页声明，不能将原始字节与折算配额相比。
  周期切换时用量与总额一起切换；永久累计单独展示。例：上期 80 GiB、本期 30 GiB、
  本期额度 100 GiB，应返回 `30/100 GiB`，不能返回 lifetime 的 `110/100 GiB`。
  > 注意别照抄不做配额的系统：那种系统里 `total` 是给客户端看的假值。
  > 本项目有真实闸断，填假值会让客户端显示与实际行为对不上。
- **`Content-Disposition`**：从**已授权用户的账号名**生成 ASCII `filename` +
  RFC 5987 UTF-8 `filename*`，**响应头绝不含 token**。生产教训：最初拿 opaque token 当文件名，
  客户端导入后显示成一串乱码；等发现要改名时，**已导入的旧订阅还得让每个人手动删除重导**。
- **节点名前缀命名空间**：共享 / 个人自定义节点加 `Custom-`、SOCKS5 落地加 `Socks5-`，
  **只在生成的订阅产物里加**，数据库与配置中的原名不变。
  **`dialer-proxy` 选择项与自动拨号组的引用必须同步映射到加前缀后的名字**，不得留悬空引用——
  这是加前缀最容易漏掉、且只有在客户端里才会暴露的一处。

**生成纪律**：

- **合并顺序确定性**：基础节点 → 所属全部组的共享配置 → 个人配置；组按固定优先级 + 字典序。
  合并后校验总数上限与**跨组名称唯一性**；个人配置与共享重名返回 `409`，**不得覆盖共享**。
- **组配置加载只用已校验的组名拼路径**，绝不拿请求参数或账号字符串当加载目标；
  在隔离作用域内先初始化空结构再加载。**文件存在但校验失败 → 整份订阅生成失败并告警，
  不返回部分产物**——半份订阅比没有订阅更难排查。
- **分享链接解析器是 fail-closed 白名单**：显式接受并归一化协议默认字段
  （如 VLESS 的 `encryption=none`、仅 `type=tcp` 下的 `headerType=none`），
  空值、大小写变体、未端到端支持的加密一律拒绝。每用户设自定义上游与落地的数量上限。
- **端点纪律**：订阅路径严格匹配；无效、已吊销、格式错误一律返回 `404` 且**彼此不可区分**；
  失败请求**不更新 token 的使用时间**；成功响应关闭访问日志与缓存。

### 4.8 审计（默认关闭）

节点侧 §4.8 默认关闭；启用即意味着节点上存在「用户 → 域名」明细，这是产品与合规决策，
不因计量已上线而自动成立（C24）。主控这一侧：

- **管理员的入口在用户列表的每一行**，不是一个独立的检索页：点某个用户的「查看审计」就看他的记录。
  这不只是少一页——C35 的归属裁剪本来就要求按「该用户持有该身份的区间」裁，
  **从用户进比从身份名进更不容易串号**，输入身份名的那种检索最容易漏掉裁剪这一步。
- **只索引不搬运**：默认不把审计文件全量拉回主控，按身份文件与时间窗按需拉候选片段。
- 活动文件名是 `access-<base64url(身份名)>.jsonl`，已轮转文件另带时间戳后缀。
  **编解码在主控侧做**，agent 校验精确文件名并只读已轮转文件；文件名只用于定位，不能用于判断用户归属。
- **拉取行为本身落主控审计**：谁、什么时候、拉了谁的哪个时间窗，与被拉取的数据分表存。
- 保留期与对外声明**独立于计费链路**制定；权限按 D19 的管理员全权与 D18 的本人查询规则执行。
- `audit_dropped` 位为真时在检索结果上打「本时间窗证据链有缺口」的标记——照常展示，明确标注。

**C35 的过滤顺序固定**：先验证记录的 `node / run / in / user`，关联到已批准且唯一的
`runtime_identity`（含其 generation），再核验该身份的历史用户归属，最后与请求时间窗及持有半开区间
求交（`clock_ambiguous` 区间的排除**未实现**，见 §2.2 C35 下的备注）。
JSONL 不携带 generation，须从已登记的 lineage 唯一解析；
字段缺失、关联不唯一、runtime 未批准或归属不明都不返回，不能用当前映射或同名文件兜底。
这个过滤必须发生在聚合、计数和分页之前，管理员按用户查看也一样；文件里的诊断行不能借用邻近访问行推断用户。

**语义口径必须刻意收窄，且 UI 用词要跟口径一致**（同类系统把这条写进了跨仓库契约）：

- 「访问网址」指的是**域名或 IP + 端口**，**不是完整 URL**。UI 上不得称其为「完整 URL」——
  一旦这么叫，就等于对外承诺了一个系统根本没有采集的东西。
- **节点采集范围与页面展示范围分开声明**：`plus_v3` JSONL 包含目标、协议、完整身份关联字段、
  写出记录时的墙钟 `ts`、连接上/下行字节 `up / down` 与连接时长 `ms`。连接关闭后才投递记录，
  `ts` 是 writer 写出时刻，不能当作精确的首次访问时间；没有独立的开始/结束事件流。
  节点不采集 URL 路径、参数、载荷内容或真实客户端 IP。个人 API 只返回目标汇总、记录时间和次数等
  展示字段，不返回原始字节量与时长；页面“不展示”不能写成节点“不采集”。
- **成功判据区分协议**：TCP 要求同一 relay 的 `up > 0 && down > 0`；UDP 只要求 `up > 0`，
  不要求收到回包。筛选规则以节点源码及对应审计测试为准，输入清单见 `docs/integration-contract.md`。
- 诊断记录（producer 缺口、窗口争用、spool 缺口）**不是用户访问记录**，
  在健康与告警界面展示，**不混进用户访问统计**。
- **不得把 sequence 缺号自动换算成「确定丢失了多少次访问」**——那是把未知伪装成已知。
- **合法配置下的审计故障不得等待、拒绝或终止数据面**：允许漏记，以有界的诊断披露代替阻塞。

#### 普通用户查看自己的出站目标（D18）

**跟随本节的全局开关，不单独再开一层。** 审计默认关闭；一旦启用，自助查询随之可用。
理由是它们是同一个产品与合规决策：既然已经决定「节点上存在用户 → 目标的明细」，
那么**让数据主体看到关于自己的那部分，比不让看更站得住**。反过来，全局关闭时这一页不存在，
不是「无权访问」——没有记录可看和不让你看，是两回事。

两个正当理由，第二个是管理员视角给不了的：

1. **数据主体访问**：这是关于他本人的记录。
2. **发现凭据盗用**：只有用户本人认得出哪些目标是陌生的。管理员看一列域名看不出异常，
   用户一眼就能发现「我没访问过这个」。这是自助查询的主要价值，不只是合规义务。

**完整身份核验与归属时间窗裁剪都是硬要求（C35）**，执行本节前述过滤顺序。

**这一页不叫「访问记录」，也不叫「网址」。** 叫**出站目标**。
「网址」这个词本身就在承诺 URL，而系统采集的是域名或 IP + 端口。管理员知道这个口径，
普通用户不知道——他会把这一页当成完整浏览历史。因此用户侧的措辞要比管理员侧更严，
页面上直接写明记什么、不记什么、以及**为什么会缺**：

- TCP 要**同一 relay 已成功转发至少一个上行和一个下行字节**才产生记录，握手即断或只发不收的
  TCP 不出现；UDP 成功发送过数据即可产生记录，即使没有回包。记录在连接关闭后投递。
- 展示域名或 IP + 端口，不含路径、参数、内容；节点另采集连接字节量与时长，本页不展示。
- **活动文件也读，按字节偏移增量**（2026-09-19 修订，偏离 C23 原文）。原方案只读已轮转文件，
  而节点只按 `max_bytes` 轮转、不支持按时间轮转。在四台上实测的真实速率下：

  | `max_bytes` | 忙的身份（8.4 KB/分） | 闲的身份（185 字节/分） |
  | --- | --- | --- |
  | 16 MiB（线上值） | 1.4 天 | 63 天 |
  | 64 KiB（节点允许的下限） | 8 分钟 | 5.9 小时 |

  调小 `max_bytes` 治不了根：轮转按**每个身份自己的文件**算，闲的身份怎么调都要等几小时到几天，
  而这一页在第一份归档出现之前是空的。

  **偏离的技术前提是查过的，不是假设**：节点以 `O_CREATE|O_RDWR|O_APPEND` 打开活动文件，
  且 `repairTrailingNewline` 只补一个换行符、**从不截断**（`audit.go:650-670`）。
  所以它严格只追加，按偏移读、截到最后一个 `\n`，就永远读不到半行——
  而「可能读到半行」正是 C23 那条读取规则的全部理由。
  `mv`-not-`rm` 那一半**不变**。

  代价照记：可见延迟变成同步周期（线上 600 秒），但**仍然没有上界**——一次同步失败就会拖长。
  UI 不承诺任何分钟数，也不能把「没有记录」解释成「没有访问」。
- **排除名单（2026-09-20 启用）**：`access_log.exclude_hosts` 35 条域名后缀 +
  `exclude_ips` 5 条网段。拿线上 31063 条真实记录量过，**排掉 85.6%**，剩 294 个目标。

  三条语义决定了它怎么写：匹配的是**将要写进记录的 `host` 字段**，不是路由解析出的
  地址——于是 `exclude_ips` **只能命中 `host_src=ip` 的记录**，它是「没东西可嗅时的
  兜底」而不是 hosts 的重复；后缀按**点边界**匹配，`google.com` 命不中 `google.com.hk`
  也命不中 `evilgithub.com`；命中的连接在 `newConnState` 就不挂 audit，于是
  **既不进文件也不占 seq**，seq 连续性仍是有效的完整性校验。

  **代价**：被排掉的流量**照样计费、照样扣额度**（检查够不到计数器），于是审计不再
  是全量，「查不到」不等于「没访问过」。所以响应必须带 `excluded`、页面必须把名单
  说出来——不说的话，一个看到 294 个目标的人会以为那就是他去过的全部地方。

  名单**取自文件里的 `ev=filter` 行，不取自配置**（配置在节点上，主控看不到），
  并带 `consistent`（这段时间里规则变没变）与 `observed`（有没有读到过那一行；
  假不等于「没有排除」）。规则不一致时取**并集**：少说的那几个正是读者会以为
  「我没去过」的目标。

  **改排除规则必须 restart 而不是 reload**，尽管 plus 接受 reload：规则一变，
  同一个 runtime 的文件里就同时有两套规则下写出来的记录，而 `ev=filter` 行
  **没有 ts**，事后说不出分界线在哪一条。restart 让「一个 runtime 恰好一套规则」成立。

- **节点日志等级降到 `fatal`**（同一次改动）。排除规则只管审计文件，管不着上游的
  日志——上游给每条连接失败写一行 `connection: open connection to <目标>`，实测两天
  18564 条、其中 82 条带域名。一边在审计里排掉 google.com、一边在 journald 里留着
  别的目标是自相矛盾的。上游 v1.14 的 `log` 段只有 `disabled / level / output /
  timestamp`，没有按连接过滤的开关，所以只能调等级。
  **代价**：丢掉 `访问审计丢弃：<原因>`（`audit_dropped` 这一位仍在快照 health 里，
  但**原因**无处可查）、`拒绝配额全量表：… 未知身份=…`，以及 audit writer 的 panic 行。
  要同时留住这些又去掉上游那些连接行，只能改节点软件。
- 审计响应返回 `archive_delay_bounded=false`、`archive_state`（`available / no_data / unavailable`）
  及过滤后记录的 `latest_available_event_at`（无可返回记录时为 null）。该时间只是已取到记录的最新时间，
  **不是完整覆盖水位**；不得据此声称此前所有访问均已归档。读取失败明确显示不可用，不能伪装为空列表。
- `audit_dropped` 为真的时间窗照常展示并标「本时间窗证据链有缺口」——
  对用户尤其要标，否则缺口会被读成系统在隐瞒。

**查看行为仍然落审计**，但按**一次查询**聚合，不是每次翻页一条；另加限频。
自助把这条链路的量级放大了一个数量级，逐页记录会把审计表本身冲垮。

个人端点为 `GET /me/audit/access`，支持 `admin / user`，目标用户固定取服务端会话主体，
拒绝客户端提供用户 ID、身份或文件路径。管理员代查另走 `GET /users/{id}/audit/access`。
两者支持 `from / to / cursor / limit`；cursor 绑定调用主体、目标用户与查询窗口，每次翻页重新检查
会话、角色、全局开关和 C35。关闭时对已认证且有端点权限的调用返回 `409 audit_not_enabled`；
普通用户调用管理员端点仍为 403。成功查询每次生成一个 `query_id`，翻页沿用它聚合留痕，且每页都限频。

**会话暴露面：接受，不加二次确认。** 加上这一页之后，一个被盗会话能拿到的从
「订阅地址 + 用量数字」变成「还有出站目标历史」。不加门禁的理由是**比例问题**：
同一个会话已经能拿到订阅地址，那是更大的战利品——拿到它等于拿到整条链路的使用权。
再加一道二次确认挡不住已经被盗的会话，只会让正常使用变烦。
真正的对策在会话本身（§4.9 的 HMAC 证明、strict 模式、可主动吊销），不在这一页。
> 这条是在「小众产品、单人管理」的前提下做的取舍。若将来用户规模或数据敏感度变了，
> 重新评估的是这个前提，不是这一页的实现。

### 4.9 身份与 RBAC：飞书 / 企业微信扫码登录

**provider 抽象**：`paoyou`（泡游 SSO，承载飞书实名，**当前在用**）| `feishu` | `wecom` | `local`（break-glass）。
飞书 / 企业微信的直连 OAuth 属于 §7 M5 的另一半，**尚未实现**；下面那张两家差异表
描述的是那一半，不是现在跑着的这条路。接泡游的落地决策见 D27。

**长期身份档案只存三个字段**：`provider` + `external_id`（飞书 `open_id`/`union_id`，企业微信 `userid`）+ 显示名。
不存手机号、邮箱、头像 URL 或全量部门树。授权另保留最小短期事实：账号是否有效、
参与规则判断的部门/组 ID、核验时间和到期时间；只覆盖当前登录账号，退出后按会话保留期清理。
历史映射结果只供审计，不能成为当前授权依据。

**角色只有两种：管理员与普通用户。**

| 角色 | 登录后入口 | 权限 |
| --- | --- | --- |
| 管理员 `admin` | 控制台总览 | 管理节点、用户、全局额度、凭据与审计；也可访问自己的个人中心 |
| 普通用户 `user` | 个人中心 | 使用自动授权的默认节点，查看自己的订阅、周期额度与用量；审计启用时可查自己的出站目标，不能访问管理数据和写接口 |

管理员由服务端配置明确指定；受信任身份提供方认证通过且账号有效的其他账号，默认成为普通用户。
角色不由客户端选择或声明，不再保留运维子角色、独立 member 身份或“已登录但无角色”分支。
停用账号、认证失败和过期成员事实仍拒绝访问，不等同于默认普通用户。

> **2026-09-18：这一段已被 D28 推翻，尚未实现。** 首次登录只建业务用户，
> 账号池领取与订阅生成是 `proxy-manager user grant` 的显式动作。理由见 D28。
> 下面这段保留原文，因为它仍然是这条路径**将来**要走到的形态。

**首次登录自动授权节点。** 管理员配置默认节点组；首次进入时，服务端创建业务用户，
从 D11 预分配账号池领取对应节点的计费身份，建立授权关系并生成订阅，无需逐个节点申请。
授权范围是管理员选定的默认组，不自动扩展到全部机群。受限用户只分配支持配额的 `plus_v3` 节点；
身份零基线、runtime 批准与预算门禁仍须满足。

- 分配以用户和节点为幂等键，身份领取与授权记录同事务提交；重复登录不重复分配、不重置用量。
- 节点不健康或账号池不足时，账号仍是普通用户，个人中心显示节点开通进度与失败原因，后台重试；
  只输出已成功授权且可用的节点，不把未开通状态当成第三种角色。
- 管理员的显式撤销优先于默认授权；后续登录不得重新授予被撤销节点。
  默认组变更对新用户生效，存量授权调整由管理员明确执行并记审计。
- 个人中心只显示自己的订阅、节点代号、用量及审计启用后的出站目标；不返回其他用户资料或管理面的地址、端口与转发链细节。
  所有个人 API 均以服务端会话主体限定查询范围。

> **前端隐藏不是安全边界。** 导航按主体收敛只是让界面讲得通；
> 越权请求必须在服务端被拒绝，拿不到的数据根本不该出现在响应里，
> 而不是「发过来再藏起来」。这与 D13 的每请求重新求值是同一条。

**每请求求值规则，成员事实有明确刷新期限（D13）**：本地授权规则变更在下一个受保护请求生效。
上游离职/转岗要等成员事实更新，不能靠重读本地文件发现；没有 IM 事件回调也不承诺上游变更即时生效。

- 登录时查询当前账号有效性与所需部门/组；活跃会话按需/后台复核，成员事实 TTL 默认 **60 秒**，可配置。
  受保护请求发现事实过期，必须先刷新再决定授权；不允许使用过期事实继续放行。
- 上游返回停用/离职时撤销该主体全部会话；转岗时替换成员事实并重新计算角色。
  刷新失败、权限不足或字段无法证明有效性时拒绝受保护请求，明确显示认证依赖不可用。
- 限频与单飞共享刷新结果，但不能延长 TTL。上游可见变更后，旧授权最多使用一个 TTL；
  上游自身传播延迟另行披露，UI/API 提供最后核验时间和失效期限。
- 本地应急禁用/撤销会话在每请求检查，下一次请求立即生效；该机制与上游成员同步独立。

- 管理员规则与节点组标识**大小写敏感**；管理员规则明确命中才提升为 `admin`，否则为 `user`。
- 授权配置缺失、损坏或非法 → **fail closed，整个认证请求失败**；
  只有成功校验配置和账号有效性后，才应用默认普通用户规则。
- 读授权源要做 TOCTOU 硬化：`lstat` → 验普通文件 → 验大小 → 共享锁 → `fstat` 复验
  dev/inode → 读取 → 验长度精确相等 → 读后再复验。
- 授权规则小文件可按 mtime + inode 缓存内容；成员事实只能在上述 TTL 内缓存。
  **每请求仍检查会话撤销、事实新鲜度并求值角色**，不能缓存最终授权结论。

**会话**：`__Host-` 前缀 + `HttpOnly` + `Secure` + `SameSite=Lax` cookie，服务端会话表可主动吊销，
写操作走双提交 CSRF token。会话不放任何 IM token。

**OAuth 回调的五项加固**（同类系统的生产实现，逐条都挡住过一类问题）：

1. **`state` = 签发时间戳 + 随机量 + HMAC**，用严格正则锁死格式，允许小幅时钟前偏。
2. **回调专用 HttpOnly Cookie** 与 `state` 绑定，作用域限定在回调路径。
3. 顺序固定为：清 state cookie → 拒绝未知 query 参数 → **无任何写入地**校验签名/绑定/TTL →
   调上游换取身份 → **成功之后**才以墓碑哈希原子消费该 `state` → 建会话 → 重定向清掉 URL 里的 token。
   **匿名伪造的回调不创建会话、不写数据库**——否则登录入口就是一个免认证的写放大入口。
4. 受保护路由额外要求**会话 ID 的 HMAC 证明**；strict 模式替换旧 ID 时立即销毁新建的空会话并拒绝。
5. 出站调用硬化：限定 HTTPS、禁跟随重定向、响应体上限、逐字段限长并拒绝控制字符。
   失败一律统一跳转，**日志只记异常类型，不记 token**。

> **两个必须实测而非照文档假设的点。** 其一，上游换取身份的接口实际接受什么 content-type——
> 同类系统踩的坑是上游只吃 `application/x-www-form-urlencoded`、不吃 JSON，
> 而文档里没写。其二，**上游字段名不一定符合语义**：同类系统的上游返回一个名叫
> `wxwork_id`（企业微信）的字段，实际承载的却是飞书标识。
> 本项目的内部字段一律**按实测语义命名，不按上游字段名命名**（§9 D5）。

**break-glass 本地管理员**：Argon2id，**默认禁用**，启用要写配置且登录后强制二次确认。
存在的理由很具体——企业微信可信 IP 一旦因为主控换 IP 而失配（§2.4），IM 登录会整体失效，
那时不能把所有人锁在门外。

**两家的差异必须在设置页里说清楚**，否则部署时一定卡住：

| | 飞书 | 企业微信 |
| --- | --- | --- |
| 应用凭据 | `app_id` / `app_secret` → `tenant_access_token`（2h，集中缓存 + 提前刷新） | `corpid` / `corpsecret` → `access_token`（集中缓存） |
| 网页登录 | 授权码 → `user_access_token`，最小只读 scope | `snsapi_base` 静默授权拿 `userid`，**不用** `snsapi_privateinfo` |
| 前置配置 | 重定向 URL 白名单 | **先**配可信域名或接收消息 URL，**再**配企业可信 IP，否则 `60020` |
| 出口 IP | 可选白名单 | **强绑主控出口 IP**（§2.4，风险见 §10 R5） |

### 4.10 通知：告警与日报

**两条通道，第二条是降级路径**：

1. **应用消息**（需应用凭据，可指向个人或群，卡片可带「打开控制台」深链）；
2. **群机器人 webhook**（不需要应用凭据）——应用凭据过期、可信 IP 失配、通讯录权限被回收时，
   通知能力不应该跟着一起没。这条通道只发纯文本摘要，不发明细。

**卡片不带写操作按钮**：本轮没有 IM 写路径，卡片上只有信息和深链。这同时意味着不需要处理
「卡片被转发到别的群后按钮被别人点」这类越权问题。

**告警规则表**：

| 规则 | 触发条件 | 级别 | 动作 |
| --- | --- | --- | --- |
| 计数倒退 | `sequence` 前进但四向任一倒退 | P0 | **失败关闭**该节点采集，不猜测、不继续收费，人工介入（C5） |
| 快照不可入账 | 计数器溢出或 `sequence` 溢出 | P1 | 停入账与正额度刷新；通道可用时将该节点全部受限身份置零（C33） |
| 身份数越界 | `identity_limit_reached` 为真（仅 `plus_v3`） | **P0** | 与上一行不是一回事：**该位粘滞、不会自愈**，该 runtime 余下时间全部不可入账，唯一恢复手段是完整重启换 runtime（C29）。立即安排维护窗口，不要当成一次普通的不健康快照等它恢复 |
| 身份数逼近上限 | 已配置身份数 / `max_identities` 超过阈值 | P2 | **扩不动了**：再加身份就会撞 C29。提前安排排空窗口扩容——撞线那一刻已经停止计费，这条的价值全在「提前」 |
| 可分配身份不足 | 池中未分配身份低于阈值 / 耗尽 | P2 / P1 | **新用户上不来**（与上一行是两回事：这条是池子空了，上一行是池子撑不大了）。耗尽时分配必须给明确错误码，不得静默复用已分配身份（D11） |
| lineage 消失 | 已观察过的 lineage 在后续快照中不见了 | P1 | 整份拒绝 + 人工介入（C25）——这是控制面与数据面已经不一致的信号 |
| 节点时钟偏移 | `collected_at` 与主控 `received_at` 偏差超阈值，或节点未同步 NTP | P1 | 告警（C27）。偏差过大时归桶回落 `received_at` 并标 `time_quality = fallback` |
| 控制面不一致 | `PUT /v3/quota` 返回 400 未知身份 | P1 | 告警 + 等新 lineage 后重推（C15） |
| 未闭合窗口 | 重启但无「已排空 + 最终快照已入账」记录 | P1 | 单独归类并保留在告警里，披露可能丢尾；**不当作正常周期切换** |
| 审计丢弃 | `health.audit_dropped` 为真 | P2 | 告警，**照常入账**（C4） |
| 序号跳号 | `sequence` 前进但跨过若干值 | P2 | 告警并记录缺口（C26）。**照常结算累计差值，但绝不对缺失时段插值** |
| 采集失败 | 连续 N 次非 200 / 连接重置 | P2 | 退避重试，超阈值告警 |
| 未知 runtime | `runtime_id` 变化 | P2 | 旧窗口对账、新 runtime 批准；先零额度收敛，健康结算后再恢复正额度 |
| 序号停滞 | 连续 N 轮 `sequence` 不变且有活跃会话 | P2 | 告警（可能是采集被挡在 429 上） |
| 证书临期 | agent / 主控证书 30 天、7 天 | P2 | 告警 |
| 额度水位 | 用户池已用 80% / 95% / 耗尽 | P3 / P2 / P2 | 通知；提频按 §4.5 的预计剩余时间与有效需求样本，不由百分比单独决定 |
| 成员事实过期 | 超过 TTL 且刷新失败 | P1 | 拒绝依赖该事实的受保护请求，显示认证依赖不可用 |
| 配额 409 | `runtime` 或 `epoch` 不符 | P3 | 自动纠正；连续失败升 P1 |
| token 陈旧 | 订阅 token 超过 N 天未轮换 | P3 | 汇总进日报 |

**限频与合并**（对齐 §2.4 的平台限制，也防止节点抖动刷屏）：
同一 `(node, rule)` 指纹去重 + 静默窗口（默认 10 min）+ 全局令牌桶（保守取每分钟个位数），
溢出的合并成一条摘要。**通知失败本身要可见**：连续 N 次失败 → 切降级通道 → 仍失败则在
Web 控制台顶部挂常驻红条——静默失效的告警系统比没有告警更糟。

**维护窗口静默**：排空与证书轮换会主动中断采集通道，窗口内该节点的采集失败类告警
（采集失败、序号停滞、快照不可入账）应被窗口标记吸收，**但 P0 与控制面不一致类告警不吸收**。
窗口结束后必须显式核对「开放告警为 0」才算收尾，不能让窗口把真实故障一起盖掉。

> **IM 通道是从零开始的。** 同类系统的告警只落数据库 + journald，没有任何 webhook 实现可搬。
> 可复用的只是告警**抽象**（一个 `open()` / `resolve()` 的 sink 接口），飞书与企业微信的
> 出站实现、限频、降级都要自己写。§7 的 M5 工期要按这个前提估。

**日报**（默认每日 09:00）：各节点入账、Top N 用户、周期水位、以及四项判据计数
（负增量 / 未知 runtime / 重复 sequence / unhealthy 入账）。节点侧 7 天长跑里这四项全为 0，
把它们放在日报第一行，等于每天复核一次结算链路是否还健康。

### 4.11 Web 控制台

**API-first**：Web 是 API 的一个客户端，页面上能做的每件事都有对应的结构化端点。
这是仓库根 README 的口径（明确输入、结构化输出、有用的失败），也让日后要加 ChatOps 时
不必回头重构。

**沿用 `web-standard-kit`**：零依赖、`wsk-` 命名空间、单 `@layer wsk`、浅深色令牌、
hash 路由、`<dialog>` + `showModal`、WAI-ARIA 键盘模式、`prefers-reduced-motion` 降级。

**多实例已经不是问题了。** 计划书早先版本记着一条前置工作：kit 的
`initMenu` / `initDataTable` / `initDialog` 按固定 id 绑定、只支持单实例，控制台一页多表必然撞车，
所以 M4 要先把它们改成多实例并回流。**这件事已经做完，而且做得比当时设想的更彻底**——
kit 现在所有监听器一次性绑在 `document` 上，通过 `closest()` 匹配 `data-*` 契约，不持有元素引用
（`web-standard-kit/script.js` 的 `mount()`）。同一页面多实例成立，片段替换后也不会产生死控件。

本项目要做的只剩一件：**片段替换后调用 `wsk.mount(root)`** 让新节点完成初始渲染，
省略参数即整个 document，幂等可重复调用。M4 不再有 kit 改造这一项。

**u64 到前端一律走十进制字符串**（C3）。前端只做格式化展示；确需运算（进度条百分比）时用 `BigInt`，
禁止 `Number` 参与字节运算。指标大数字用 kit 已有的等宽数字与展示字阶。

**图表**：kit 不含图表组件，而总览与用量页必须有趋势图。采用 **vendored 图表库**
（许可证文件随静态资源一起提交，**不走公网 CDN**），因此 §5 的「零依赖」口径相应放宽为
「无构建步骤、无包管理器，第三方库以 vendored 形式随二进制发布」。三条纪律：

- **tooltip 用服务端返回的十进制字符串格式化**，不要把展示用浮点当精确流量值。
  这是 C3 在图表层的延伸——C3 原本只覆盖到 API 边界，而图表恰恰是最容易把字节喂进
  `Number` 的地方。
- **请求序号门禁**：筛选器变化会并发发请求，**晚到的旧响应不得覆盖新选择**；
  不同视图（个人 / 管理员）各维护独立图表实例。
- **深浅主题切换要重建图表配色；隐藏面板重新显示时要触发 canvas resize。**

**前端安全与缓存口径**：

- 主题脚本用**外部 `assets/theme.js`** 在首屏 CSS 之前执行——既避免主题闪烁，
  又满足 `script-src 'self'` 的 CSP（页面内无 inline script）。
- 登录态页面 `Cache-Control: private, no-store` + `Vary: Cookie`，
  避免不同登录态的内容被共享缓存串台。
- 面板位置用 URL hash 保存，并同步活动导航与键盘焦点（kit 的 hash 路由已有）。

**页面与组件对应**：

**一页一个 URL。** 侧栏每条链接对应一个真实页面，不是 hash 路由——
这与 M4 的服务端渲染形态一致，也让越权在服务端就能拦住，而不是先把整个应用发过去再藏。

| 页面 | 文件 | 可见主体 | 关键点 |
| --- | --- | --- | --- |
| 登录 | `login.html` | 未认证 | 单独成页（缓存头与登录态不同）。**一个泡游 SSO 按钮**（D27），点了就跳；飞书 / 企业微信直连 OAuth 未实现；break-glass 默认折叠 |
| 我的订阅 | `me.html` | 管理员、普通用户 | 默认节点自动授权结果、订阅地址、本周期额度、计费口径说明 |

**静态原型已经在 `web/` 下了**，全部页面可点：

```bash
python3 -m http.server 8173 --directory <仓库根>
# 然后打开 http://localhost:8173/sing-box-plus-manager/web/index.html
```

原型使用示例数据，尚未连接认证与授权服务。`assets/app.js` 负责两种角色的预览分流、
响应式导航与趋势图；普通用户页展示默认授权成功的样例，设置页的保存不写入服务器。它的价值是**把口径变成看得见的东西**：
地板失效、超发没有有限上界这件事、审计归档延迟无上界，
这些在表格里是一行字，在界面上是一个必须有人决定怎么显示的格子。

原型与正文的对应关系：

- **样式与脚本相对引用同仓的 `web-standard-kit`**。M4 的做法是**构建时 `include_str!` 嵌入**
  并按摘要锁定，而不是复制一份进 `assets/`——复制会产生第二个副本，
  而两个副本里总有一个先过期。页面里写的 `../../web-standard-kit/style.css`
  从 `/overview.html` 解析出来正好是 `/web-standard-kit/style.css`，
  直接 `file://` 打开时又指向兄弟目录：**同一个路径两边都成立**，所以页面一个字都不用改。
- **一页一个文件**，外壳（顶栏 / 侧栏 / 页脚 / 对话框）在各页重复，因为原型没有构建步骤；
  M4 由服务端渲染一次，那份重复不存在。改外壳时要么全局替换，要么先写生成脚本。
- **`assets/console.css` 包含控制台外观与原型角色显隐**；真实实现保留视觉样式，
  角色判定与数据裁剪必须迁到服务端，不能依赖 CSS 或 localStorage 授权。
- **指标卡的大字放量级，精确字节放小字**。kit 的指标字阶是给「1,248」设计的，
  15 位的字节数会直接溢出卡片——这是原型跑出来才发现的。
  精确值仍在页面上、仍可选中，C3 也仍成立。
- **图表已换成 vendored uPlot**（MIT，`web/vendor/`，许可证随二进制一起发，运行时不走 CDN）。
  C3 的纪律照搬并且收得更紧：**整个前端只允许一处把字节转成浮点**，
  就是 `assets/chart.js` 里的 `toPixelScale`，由 `tests/m4/assets.rs` 机械断言
  「恰好一处、且必须叫这个名字」。tooltip、图例与明细表一律回查服务端返回的十进制字符串。

## 5. 技术选型与目录结构

仓库子项目 ID 与源码目录统一为 `sing-box-plus-manager`。在仓库根进入项目并运行测试：

## 6. 主控对外 API

统一前缀 `/api/v1`。设计口径照仓库根 README：**明确输入、结构化输出、有用的失败**。

- **所有字节字段是十进制字符串**（C3）；时间是 RFC 3339（UTC）。
- **每份快照保存三个时间，且归桶选择结果必须持久化**（否则重放同一批次会落进另一个桶）：

  | 字段 | 来源 | 用途 |
  | --- | --- | --- |
  | `collected_at` | agent 完成采集的时刻 | 时间质量判定 |
  | `received_at` | 主控收到响应的可信时刻 | 偏差核对；`collected_at` 不可信时的回落值 |
  | `accounting_at` | 主控按规则生成 | 增量归属的时间桶 |

- **小时桶用 UTC 整点 + 半开区间 `[start, end)`；日桶用一个持久化的展示时区**，
  按该时区的日历日计算——**不能写成「前一日开始时间 + 24 小时」**（夏令时与跨月会错）。
  改展示时区必须完整重建日缓存，API 必须回传当前时区。
- **口径三元组随事实一起固定**：`metric_scope`（计费边界）、`traffic_estimated = false`、
  `time_bucket_estimated = true`。这描述已接受快照的字节口径，不表示没有未闭合窗口。
  同一健康 runtime 的时间不确定范围是**两次成功采集的实际间隔**；API 另回传观察窗口、
  `observation_gap_ms`、时钟质量和跨周期估算标记，旧 runtime 丢尾单独披露（R4、R11）。
- **错误对象形状固定**，不随端点变化：

  ```json
  { "error": { "code": "quota_stale_epoch", "message": "…", "detail": { "node_id": "…", "expected_epoch": "138" } } }
  ```

  `code` 是稳定的机器可读枚举（人和 Agent 都按它分支），`message` 给人看，`detail` 给排查用。
- **写操作要幂等键**（`Idempotency-Key` 头），**更新要乐观并发**（`If-Match: <revision>`）。
- 分页统一 `?cursor=&limit=`，返回 `next_cursor`，不用 offset。

| 方法与路径 | 作用 |
| --- | --- |
| `GET /nodes` `GET /nodes/{id}` | 节点清单与详情（health 四位、capabilities、最近 sequence、runtime 窗口） |
| `POST /nodes/{id}/collect` | 手动触发一次采集，仍走单飞与全部校验。停机前必传 `expected_runtime_id`；原始快照持久化后返回含 `runtime_id / sequence / payload_sha256` 的采集回执，不表示已入账 |
| `GET /identities` | 计费身份（六元组展开），支持按节点 / 用户 / `active` 过滤 |
| `GET /users` `POST /users` `PATCH /users/{id}` | 用户与节点授权。**没有 per-user 额度字段**——额度是全局设置（D21） |
| `GET /users/{id}/usage` | 周期用量、池剩余、各节点分配额 |
| `GET /settings/quota` `PUT /settings/quota` | 全局月度额度（D21）。调低先 `dry_run=true` 预览再确认；实际提交落审计并返回 `202`、revision、受影响人数与逐节点下发状态。立即触发新采集→结算→全表下发；`GET` 返回当前 revision 与同一组状态，未确认的节点显示待生效（§4.5） |
| `POST /users/{id}/quota:recalc` | 排队重算；没有未占用的新鲜 sequence 时主动采集。按节点合并所有受限用户后下发，不直接推送单用户清单 |
| `GET /subscriptions/{user_id}` `POST /subscriptions/{user_id}:rotate` `DELETE …` | 订阅 token |
| `GET /nodes/{id}/settlement-status` | **只读停机门禁**：必传采集回执的 `runtime_id / sequence / payload_sha256`，返回该确切批次的状态与 `drained`，不得回落到“最新快照”。只有 `applied` 且排空证据成立才允许正常关闭窗口；完整契约见 `docs/operations.md` §3 |
| `GET /me/audit/access` | 本人出站目标（`admin / user`），目标固定为服务端会话用户，不接受用户 ID、身份或文件路径。支持时间窗与分页；每页检查全局开关及 C35，一次查询聚合留痕、每页限频（§4.8） |
| `GET /users/{id}/audit/access` | 管理员代查某个用户的出站目标（仅 `admin`）。与个人端点共用 C35 的完整身份过滤、归属裁剪、归档状态和分页规则；行为本身落审计 |
| `GET /alerts` `POST /alerts/{id}:silence` | 告警与静默 |
| `GET /healthz` `GET /readyz` `GET /metrics` | 自身健康与指标 |
| `POST /auth/logout` | 退出并吊销当前会话。**是写操作**，走双提交 CSRF——否则任何第三方页面都能把人踢下线 |

**登录入口不在 `/api/v1` 下**：`GET /auth/sso/login` 与 `GET /auth/sso/callback`
是浏览器顶层导航，不是结构化 API，响应是 302/303 而不是 JSON（D27）。
两者**只在配了 `[sso]` 时挂载**——没配就是 404，而不是一个会 500 的按钮。

**订阅端点独立**：`GET /sub/{token}`，不在 `/api/v1` 下，不认会话，只认 token，单独限流（§4.7）。

## 8. 测试与门槛

**结算故障矩阵**（对照 §2.1 每一条，M1 的准入门槛）：

| 注入 | 期望 |
| --- | --- |
| `sequence` 重复 / 回退 | 整份丢弃，基线不动，无计费记录 |
| 四向任一倒退 | 失败关闭 + P0 告警，无计费记录 |
| 不可入账的 health 位为真 | 不入账、不刷新正额度；尝试下发完整零额度安全表 |
| `health.audit_dropped` 为真 | **照常入账** + P2 告警 |
| `health` 多出一个键 | 整份拒绝 |
| `schema_version` 与路径错配 | 整份拒绝 + 告警 |
| HTTP 429 / 连接被重置 | 可重试、不入账、状态不变 |
| `Content-Length` 不符 / JSON 截断 | 拒绝入账 |
| `2^63−1` / `2^63` / `u64::MAX` 与跨 u64 聚合 | 精确解析、20/39 位 SQLite 文本往返和排序正确；API 字符串；checked u128 溢出回滚 |
| 账本/累计/游标事务中途 kill -9 | 对已持久化输入恢复后不重复不漏记，四张事实/状态表一起回滚或提交 |
| `runtime_id` 变化 | 旧窗口审计、新 runtime 显式批准；先零额度，健康结算与预算门禁通过后恢复正额度 |
| `active=false` 后又回来 | 基线延续，不归零（C2 C9） |
| 已观察的 lineage 从快照里消失 | 整份拒绝，**不解释成零增量或删除**（C25） |
| `sequence` 跳号 | 照常结算累计差值 + 告警，**不对缺失时段插值**（C26） |
| 批次乱序到达 | 按最小未处理 `sequence` 结算；更旧且未处理的标 `superseded` |
| `health` 多一个键或少一个键 | 整份拒绝——闭集是「不多不少」（C4） |
| 节点时钟快/慢超阈值 | 归桶回落 `received_at` 并标 `time_quality = fallback` + 告警（C27） |
| 账号池耗尽 | 分配失败有明确错误码，不静默给出重复身份；触发 P1（D11） |
| SIGHUP 把身份数推过 `max_identities` | `identity_limit_reached` 置位后**粘滞**：后续快照一律不入账，且不随下一次 SIGHUP 恢复；只有换 runtime 才清除（C29）。这条必须在真实节点上跑，夹具造不出粘滞语义 |
| 大量 `active=false` 残留后再扩容 | 身份计数按含 `active=false` 的总数判定，不是按活跃数——用例要先制造残留再逼近上限（C29） |
| 停采多轮后同 runtime 恢复 | 累计差分补回，时间窗口按实际成功采集间隔标记，不按一轮估算 |
| 停采期间节点崩溃或重启 | 旧尾账不声称已恢复；窗口标 unclosed，新旧计数不相减 |
| 清理明细、重复清理、恢复备份 | lifetime 与已结算周期累计不减不重复；未结算/活跃周期保护生效；归档不能二次叠加 |

**配额状态机**（D16 确认在范围内，是 M2 的准入门槛）：

- 409 的 runtime/epoch 两种成因分别覆盖；node_id 配错单独拒绝。`epoch = 0` 返回 400；
  新 runtime 可用 1 发零额度表，批准、健康结算和预算门禁通过后才有正额度。
- 在“持久化请求后未发送”“节点已应用但 200 丢失”“收到 200 后主控崩溃”分别恢复，
  epoch 不重复分配、不用旧正额度机械重推。
- **全量集合断言**（C30）：entries 的唯一身份集合等于节点上所有受限用户的当前有效身份集合；
  两个用户并发重算、仅 A 耗尽而 B 尚有余额、B 在两次 A 重算间消耗，都不能解限额或补回 B 的旧额度。
  反向用例故意省略 B，必须检测其被节点解限额。
- `Unlimited` 与 `Limited(0)` 同时出现时，前者省略、后者保留；某用户池为零不生成空节点表。
- 无健康快照时连续执行三轮调度，正额度不得反复补回；零额度发送失败后恢复时先核对 runtime 再收敛。
- **C33 的肯定动作**：无新鲜快照但通道可用时，主控必须**主动下发一份全零完整节点表并拿到 200**，
  而不是什么都不做。两者在观测上完全不同——不作为会让节点带着旧的正额度一直跑到自己耗尽，
  而现有的否定面断言对一个「什么都不做」的实现同样是绿的。
- 同一健康 sequence 在 TTL 内连续触发三次手动重算，最多准备一份正额度表；其余等待新采集。
  后续重算主动排队采集，不等定时周期；队列中快照超龄时不发送旧正额度，主控重启不清除已占用 sequence。
- **改额度本周期立即生效**（D21）：已用 320 GiB 的用户，额度 300 → 500 后
  在单节点、无新增流量的夹具中，下一次 `remaining_bytes` 为 180 GiB 对应值而非 0；额度 300 → 100 后为 0。
  参数变更本身不造账；主动采集发现真实新增流量时照常入账后再计算，不能为保持旧示例余额跳过结算。
- **立即采集再下发**：刚完成正额度下发就改设置，最近 sequence 已占用，必须主动取到并结算新 sequence，
  不等定时周期、不复用旧快照；连续修改 revision 时旧任务不能恢复旧额度，完整表使用新 epoch。
- **失败状态**：主动采集超时或 health 不可入账时无正额度刷新；控制通道可用则尝试完整零表。
  `safe_zero`、`unknown`、`failed` 都不能显示为新配置已应用，恢复后按最新 revision 重试。
- **调低先预览**：相同已结算用量下，`dry_run` 名单与实际提交结果一致，预览显示用量核验时刻；
  未经确认的调低请求被拒绝。调高不要求预览。
- **改额度落审计**：一条记录含操作者、时间、旧值、新值与受影响人数。
- `used > quota` 使用饱和减法；`N=0`、`B=0`、wire 上限截断和全部权重相同均无除零/溢出。
- `[64,336] MiB` 分配、`[0,100] MiB` 用量的反例：剩余 300 MiB 时两个节点都至少取得 64 MiB；
  最大余数法结果确定，地板不因最终归一化失效；随机分配均满足总额与地板约束。
- 冷节点权重始终为正；`a_i=0` 不做除法且仍能获得探测额度。`B>=N` 时每个可更新节点有正额；
  固定 `0<B<N`、预算可回收且每轮成功收敛时，轮转覆盖所有节点；不承诺单轮恢复吞吐。
- 需求样本覆盖 `u_i/a_i = 0.99、1、1.31`，后两者不报非法计量；按阈值提频只表示需求偏高，
  不当作闸断证据。跨多个 epoch 的窗口不参与需求权重更新。
- 同节点同口径多身份的额度总和等于节点分配额；不同口径各自成池。
- 响应丢失、延迟到达与部分节点失败后，先核对 runtime 并收敛零额度，再用新健康结算重算；
  不建立在途预留、冻结或核销记录。API/UI 不提供超发上界字段或数字，明确披露 D20 的超发风险。
- `remaining_bytes` 处于 `0`、`2^63−1` 的 wire 往返正确；负值拒绝，不能将超大数隐式转为负数。

**聚合并发**（D15 换掉租约后的新机制，必须有对应用例）：
同一脏桶被调度器与手动重算同时领取时只有一方生效；
**算到一半桶又脏了** → 写回时 `version` 冲突，本次结果丢弃并重新标脏，不得覆盖；
worker 崩溃后任务回到 `pending` 且不留中间态；重复领取同一桶两次的最终合计不变。

**节点变更（D20 之后，主控只剩两个接触点）**：

- `collect` 带 `expected_runtime_id`，实际 runtime 不符时拒绝生成可用于停机的回执；
- 确认端点必须绑定回执的 runtime、sequence 与 payload 摘要。快照 10 已入账、最终快照 11
  仍未接收或未结算时不能放行；换 runtime 的同号快照、错误摘要、缺少参数同样不能放行；
- 精确批次的 `pending / rejected / superseded / conflict / unknown` 均不等于 `applied`。
  后续批次已成功不能静默代替待确认批次；需要时重新采集最终快照并使用新的回执；
- 即使精确批次为 `applied`，其中会话未归零或 gauge 不可用也不能标为正常排空；
- 新 runtime 登记后先下发零额度安全表，健康结算通过前不产生正额度（C33）；
- gauge 读取失败时手册第 2 步只能超时强切，**该窗口无条件标记未排空**；
- 未闭合窗口（崩溃 / OOM / 断电）单独归类并披露可能丢尾，不当作正常周期切换。

排空五步本身的正确性由手册与人工复核保证，不再有自动化状态机可测——
这是 D20 换来的简化，也是它的代价。

**自助审计（D18，M6 的准入门槛）**——这一组的失败模式是**把别人的出站目标交给错的人**，
所以每条都要有反向用例证明断言会红：

- **完整身份与归属裁剪**（C35）：同一节点两个入口同时使用 `X`，分别属于 A/B 且记录写入同一文件，
  查询 B 不能返回 A 的目标、计数或时间。再覆盖不同节点同名、重启后复用名称且墙钟区间重叠，
  以及同名身份先属 A 后属 B 的持有边界；故意删去任一身份维度或时间裁剪，反向用例必须失败。
- 字段缺失、未知 runtime、generation 关联不唯一、归属不明的记录不返回；过滤先于聚合与分页。
- ~~**存疑区间整段排除**：归属事件标 `clock_ambiguous` 的时间窗，对任何用户都不返回。~~
  **未实现**（2026-09-19）：那个状态值全仓只有一个 CHECK 枚举，没有写入方、没有阈值、
  没有推导代码，所以这条准入判据目前**恒为真空**。留在这里是因为它仍然是对的设计；
  但不把它写成「已实现」——在文档里声称一条不存在的保护措施，比不写它糟得多。
  真要实现，先得定义「什么叫存疑」以及谁来写那个状态。
- **一个用户多身份**（D17 情形 2/3）：合并显示时每条记录标明来源身份；
  不同计费口径的身份不混算。
- **一个名字多条协议入口**（2026-09-20）：SS 与 VLESS 的记录落在**同一份文件**里
  （`access-<b64(identity)>.jsonl` 按身份名分，不按入口分），靠记录里的 `in` 字段区分，
  两者都归本人。C35 的四值关联因此**不再把「同节点跨入口同名」判成二义**——
  判成二义的后果不是报错，是页面上安静地少了一半记录。
- **全局开关关闭时该端点返回「未启用」而不是「无权访问」**，且导航项不存在；
  开关从开到关之后，已打开的页面再次查询必须被拒绝（每请求重新求值，D13）。
- **端点授权**：普通用户可调用 `/me/audit/access`，管理员代查端点对其返回 403；个人端点拒绝指定
  别人身份，跨主体或跨时间窗 cursor 不可复用。翻页时全局开关关闭返回 `409 audit_not_enabled`。
- **采集与展示口径**：消费 plus 审计样例，TCP 的 `up > 0, down = 0` 不返回，UDP 同条件可返回；
  节点原文含 `ts / up / down / ms`，个人响应不含原始字节量与时长，页面明确说明“节点采集、本页不展示”。
- **活动文件按偏移增量读，只取完整行**（2026-09-19 修订，见上）：半行留在节点上，
  下一轮补完了才收；轮转由「出现了更新的归档」判定而**不是**由「文件变短」判定——
  后者在周期同步下会静默漏读新文件的前若干字节。
  返回归档状态与 `archive_delay_bounded=false`，不声称空列表代表没有访问或固定分钟数后就可见。
  已返回记录的最新时间不当成完整覆盖水位，读取失败不伪装为空列表。
- **查看行为落审计但按查询聚合**：一次查询翻 5 页只产生 1 条审计记录，不是 5 条；限频生效。
- **缺口标记**：`audit_dropped` 为真的时间窗返回缺口标记，且**不附带任何「丢失了 N 条」的估算**。

**前端**：三个组件的多实例并存；u64 字符串端到端；键盘可达性与 AA 对比度抽查；
`prefers-reduced-motion` 与深色首屏无闪烁（kit 已有保证，回归即可）。

**两种角色与默认授权**：管理员可访问管理页和个人中心；普通用户仅可访问自己的数据。
首次登录自动分配默认组节点；并发/重复登录不重复领取身份；账号池不足展示开通中；
管理员撤销后再次登录不自动恢复。伪造角色、跨用户 ID 与绕过导航直调管理 API 均拒绝。

**授权与订阅**：本地撤权下一请求生效；上游可见离职/转岗后到达 TTL 必须刷新，
限频/网络失败不能延长旧权限；上游停用时撤销全部会话。验证最近核验时间、过期提示和 TTL 边界。
跨周期订阅案例：历史 80 GiB、本期 30 GiB、额度 100 GiB，返回 30/100，永久累计仍为 110；
清理旧账本、清缓存、重复结算及备份恢复均不改变该关系。

**长跑**：多节点连续 7 天，四项判据全为 0，对齐节点侧 §7.1 的长跑口径。

**验收不变量**：持续断言（账本/游标/缓存/水位之间的一致性）见
[`docs/data-model.md`](docs/data-model.md)，测试与生产巡检都要跑。
收尾那句值得写在这里：**「接口返回了一个非空数字」本身不是正确性证明。**

**关于断言本身是否有效**——两条来自同类系统的教训，都是花了真金白银才发现的：

- **文本断言检查的是实现字符串，不是行为**，会因为无关原因「碰巧通过」。
  同类系统一轮清理里发现 6 处这类断言是错的或靠巧合通过。
  → **每条关键断言必须有反向测试证明它会红**：注入错误，断言必须失败。
- **特权路径上的行为必须在特权环境验证。** 生产教训：一个文件同步的选项顺序错误，
  让以 root 运行的接收端改写了整棵树的属主；**本机复现不到**，因为本地接收端不是 root，
  那个选项静默无效。→ 故障矩阵要标注哪些用例**必须在 root / 真实节点上跑**。
- **skip 不等于 pass**：把「环境不支持」的跳过退出码当作失败，不允许静默放过。

**措辞纪律**：§7 的完成标准要区分「自动化覆盖」与「生产演练」。
同类系统诚实地把账号池耗尽、配置损坏、完整回滚、证书轮换标为「未实操」，
并写明「不为补齐勾选而破坏当前生产数据」。本项目沿用这个措辞标准——
把没跑过的演练写成已完成，比没写更危险。

## 9. 决策记录

| # | 决策 | 理由 |
| --- | --- | --- |
| D1 | 新建 `sing-box-plus-manager`，不扩 `sing-box-manager` | manager 的 ROADMAP 把「Web 管理台 / 公开管理 API」写进「暂不计划」，且它的 SQLite 单写者与 SS 多跳编排是围绕另一套模型建的。扩它要先推翻两条已写死的非目标 |

| D29 | **外呼 HTTPS 手写而不是引 HTTP 客户端**：只加 `webpki-roots` 一个依赖，请求逻辑照 `src/agent/mod.rs` 的口味手写 | 需求是「一个固定端点、一个方法、一种 content-type、有界响应体」，而仓库里已有一份手写 HTTP/1.1 的现成范例。引 reqwest 会连带 hyper-util / http-body-util / tower-http 一整串，为一次外呼不值当，也与 Cargo.toml 顶上「不预先声明用不到的 crate」相左。取 `webpki-roots` 而非 `rustls-native-certs`：无平台依赖，构建可复现。**代价**：`Transfer-Encoding: chunked` 必须自己解——`Connection: close` 不阻止对端用它，而不解的后果是 body 带着十六进制长度行被当成 JSON，报出来的是「JSON 不合法」，与「token 无效」在日志里长得一模一样。<br>与 agent 那套 TLS **不能互换**：agent 是私有 CA + 逐字节比对 leaf DER + 强制 mTLS + 不校验主机名 + EKU 必须恰好只有 `serverAuth`；公网证书普遍同时带 `serverAuth`+`clientAuth`，最后这条就会直接拒掉 |
| D30 | **`check-token` 的 content-type 与成功判据以实测为准**：`POST` + `application/x-www-form-urlencoded` + RFC 3986 编码；顶层 `code` 整数与字符串两种形态都认；`data` 先收成 `Value` 再判 | 三条都是踩过的。<br>**其一，content-type。** 出处要说准：`operations` 仓的 `docs/paoyouProxy/sso.md` 步骤 6 **写明了**「该接口读取 `application/x-www-form-urlencoded` 表单，不读取 JSON 请求体」——那是本方把实测结论补记进文档的结果，不是「文档没写只能靠猜」。外发那一份接入说明没有这句，所以只拿到外发版的人仍会踩。真正容易读反的是说明第 3 节那段 JavaScript 示例里的 `Content-Type: application/json`：它指的是浏览器打给**第三方自己**的回调端点，照抄会得到「token 不能为空」。<br>**其二，失败时 `data` 是 JSON 数组**（`"data":[]`）。直接反序列化成结构体，会让「token 为空」这个正常失败在解析阶段炸成一个看起来像上游故障的错误——告警指向泡游，而问题在我们这边。<br>**其三，字段误名。** 上游 `wxwork_id`（企业微信）装的是**飞书 `fs_id`**，主控侧一律命名为 `feishu_fs_id` |
