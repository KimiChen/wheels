# frp-plus 开发计划

更新日期：2026-10-03（Asia/Shanghai）

状态：开发中；阶段一 G1 已通过本机验收，阶段二、三待开发，写管理尚未开放。任务勾选以实际验证为准，不代表已经上线。

实施基线：`upstream.lock` 固定的 FRP v0.71.0；升级上游版本另行评估，不与功能开发混合。

## 1. 目标与实施顺序

按以下顺序推进，每个阶段通过验收后再开放下一阶段的用户能力：

1. **补齐观察详情**：远端入口、Visitor、错误原因、传输方式，以及明确的原生配置管理入口。
2. **建立配置操作闭环**：配置来源明确，完成校验、变更预览、应用、结果确认和回退。
3. **补齐运维与验证**：配置变更审计查询、隧道历史、完整备份依赖和实际使用协议的互通回归。

阶段 2 开放任何写操作前，必须先完成最小审计记录、私有恢复快照和崩溃恢复能力；
阶段 3 再补齐审计检索、导出、保留策略和完整运维体验。不能将写操作的审计推迟到阶段 3。

最初规划提交为 `23851a2`，后续开发按本计划推进。稳定的功能说明、配置示例和操作手册
汇总到根目录 `README.md`，本文件用于跟踪任务、验证证据与尚未完成的工作。当前未部署生产。

### 1.1 规划时基线事实

- 二进制仍由原生 `cmd/frpc` / `cmd/frps` 构建，补丁增加生命周期、配置段和只读快照。
- Plus 当前只管理监控节点、绑定、分组、套餐与探测，没有隧道配置写入和远程 reload 闭环。
- 现有 FRP 上报没有 Visitor、远端入口和完整错误模型；服务端只观察当前内嵌 frps。
- 监控协议严格拒绝未知字段，首个 hello 已包含旧 FRP 快照；新增字段必须考虑双向滚动升级。
- 原生 Store 单项 CRUD 的磁盘持久化与运行时 reload 不是一个事务；reload 失败不会自动恢复磁盘。
- 原生文件配置 PUT 只是写文件，不能直接作为“校验并安全应用”接口使用。
- 文件与 Store 同名时存在来源覆盖；禁用或删除 Store 条目，可能使文件中的同名条目重新生效。
- 原生 frpc reload 不等于替换全部启动配置；frps 没有同等的配置热重载入口。
- 当前备份工具依赖安装格式和固定文件白名单，拒绝 includes；现有协议测试不是完整原生功能矩阵。

代码依据：`shared/protocol.go`、`shared/frpserver.go`、`monitor/reconcile.go`、
`patches/0001-monitor-lifecycle.patch`、`patches/0004-frp-reconciliation.patch`、
`scripts/frp.py`、`scripts/ops.py`、`tests/frp_smoke.py`。
原生管理实现以锁定源码的 `client/config_manager.go`、`client/service.go`、
`pkg/config/source/store.go`、`pkg/config/source/aggregator.go` 为核查入口。
`.cache` 只是组装目录，不作为提交内容或唯一设计依据；每轮实现重新核对锁定源码和补丁。

### 1.2 首版范围与设计决策

| 事项 | 计划采用的决策 | 边界 |
|---|---|---|
| 可写配置来源 | **原生 Store 作为首版 Proxy/Visitor 的唯一托管来源** | 沿用 FRP 类型、校验和运行机制，增加整集应用与恢复适配层 |
| 已有文件配置 | 先只读盘点、展示有效配置与来源；提供显式迁移到 Store 的流程 | 不自动接管，不通过覆盖同名项实现迁移；文件保持原生管理能力 |
| 启动配置 | serverAddr、认证、TLS、telemetry、monitor、Store 路径、frps 监听等仍由原生文件管理 | 展示需重启提示、校验与维护说明；首版不承诺远程热改这些字段 |
| 原生 Dashboard | 保留，并提供明确的访问条件和经管理员设置的入口 | 不要求公网开放，不将其凭据下发到浏览器，不自动反向代理任意地址 |
| 控制通道 | 在现有独立 WSS 上协商专用配置管理能力 | 仅显式启用托管的 Agent 接收；旧 Agent 保持只读，不增加任意 shell 执行 |
| 配置权威 | Agent 本地 Store 与运行时实际状态是应用结果依据 | 主控保存操作意图和状态，不把数据库里的期望值当作已生效配置 |
| 数据持久化 | SQLite 保存操作、审计和事件；现有可选 TSDB 保存指标曲线 | 私有回退快照与脱敏审计分离；历史关闭不影响配置操作与审计 |
| 管理范围 | 当前内嵌 frps 与逐节点的单个明确 frpc Service | 跨 frps 汇总、多 Service 托管及远程进程升级不纳入首版 |
| 套餐与流量 | 延续主机账本与 FRP 隧道流量分开统计 | 不附带实现超额断网、自动限速或到期停隧道 |

对不支持的类型、字段、旧版本和配置来源，界面必须明确说明原因，不能显示一个实际无效的保存按钮。
首版未覆盖的高级配置应完整保留或拒绝编辑，禁止解析后静默丢弃再写回。

### 1.3 实施核查补充（阶段二前置约束）

- 原生 Store 的 `Load()` 读取内存；只有初始化 `loadFromFile()` 读取磁盘。
  外部 Store 文件编辑不能靠原生 reload 自动发现或生效，托管 CAS 必须同时检查原始磁盘摘要。
- 原生 Store 装载允许未知字段，重复名称写入 map 时后项覆盖。不能通过当前 typed 对象
  证明原文无损；迁移前必须严格解析原文，拒绝未知字段、重复名称和不可保留的高级内容。
- 阶段一的观察 revision 仅覆盖聚合后有效对象、来源类别和 `start`，不包含被覆盖内容、
  主文件原文、完整启动 common 或依赖文件；阶段二必须单独定义完整 CAS revision。
- 原生 Proxy/Visitor 的部分秘密是内联字符串，没有通用 secretRef。Plus 的本地引用层
  需要在 Agent 解析；最终原生 Store 及回退材料仍可能包含秘密，必须使用私有文件权限，
  不能宣称原生配置已加密，也不能将脱敏 GET 当作完整候选回写。
- `reloadMu` 只串行一个 Service，原生文件 PUT 不持有该锁。所有受支持写入口需共同
  进入托管屏障；同 Store 多 Service/多进程须拒绝并持有跨进程独占锁。
- 不遵守锁的外部编辑无法仅靠“读摘要后 rename”消除竞态。托管根目录须约定独占写入，
  手改前退出托管；CAS 前后复核、保存发现的漂移、遇到不确定性中止，明确保证范围。

## 2. 阶段一：补齐观察详情

交付目标：管理员能回答“这条代理或 Visitor 从哪里访问、采用什么传输、为什么异常、
配置来自哪里、下一步在哪里修改”，同时保留原生客户端与旧 Agent 的兼容性。

### P1-01 协议演进与私有详情契约

- [x] 定义独立详情能力 `frp.detail.v1`，与原生 wire v1/v2 分开命名。
- [x] 首个 hello 保持旧结构；通过已认证升级响应头预告能力，Agent 仅在得到预告后声明、协商接受后发送新详情方法；旧服务端不收到新增字段或能力。
- [x] 新服务端继续接受旧 Agent；新增详情使用独立 DTO/方法及时间、新鲜度和错误状态，携带 session/sequence 并与指标、探测共享单调序号空间。
- [x] 服务端仅返回客户端已声明能力的受支持子集；同时更新两端编解码与下行分发，避免旧版 Agent 因未知方法断开。
- [x] 定义 Proxy、Visitor、入口、传输、来源、错误等私有 DTO，避免直接序列化原生配置对象。
- [x] 为数量、帧大小、字符串长度、采样频率设置上限；超限显示“不完整/不可用”，主机指标继续上报。
- [x] 新详情仅进入管理 API；列表/SSE 仅发布状态和时间，完整数据按节点鉴权读取。现有公开 FRP 汇总保持原边界，不顺带暴露更多字段。

影响：`shared/protocol.go`、`shared/browser.go`、`agent/service/service.go`、`monitor/service.go`。
验收：新旧 Agent/Server 四组合、未知能力、未协商方法、重复/迟到帧、超限和断线重连；
旧端不因新增字段退出，公开 JSON/SSE 不包含新增私有详情。

### P1-02 远端入口与有效地址

- [x] Proxy 详情区分配置期望、服务端实际分配、管理员公布入口，并标注各自来源和观察时间。
- [x] TCP/UDP 采集实际监听地址和端口，包括动态分配端口；离线或未登记时不沿用旧端口冒充当前值。

- [x] 增加管理员公布访问地址的可选配置；监听地址、回环地址、通配地址不直接等同公网可达地址。
- [x] 保留服务端独有代理与原版 frpc 的展示；缺少 Agent 详情时标记“仅服务端观察”。

影响：新增顺序补丁扩展原生快照、`shared/frpserver.go`、`monitor/reconcile.go`、管理 DTO。

## 3. 阶段二：建立配置操作闭环

交付目标：管理员能对已授权节点的托管 Proxy/Visitor 完成一次可追踪、可确认、可恢复的配置变更。
原生进程重新建立代理可能造成连接中断，界面必须展示影响，不能承诺运行时无缝或跨节点原子事务。

### P2-01 来源所有权与显式迁移

- [ ] 新安装可选择启用 Store 托管；现有安装默认保持原状，Agent 本地显式开启配置管理并固定 Store 路径。
- [ ] 定义所有权约束：同一 Service 的托管对象不能同时在文件/include 中保留同名定义；检查 `start` 筛选影响。
- [ ] 导入前盘点全部有效 Proxy/Visitor、禁用项、模板/includes、来源覆盖、插件和秘密字段。
- [ ] 迁移预览同时列出“写入 Store”和“从原来源移除”的变化及需要重启的步骤，不使用同名覆盖代替迁移。
- [ ] 对任意既有文件不做自动重写；生成迁移候选与维护步骤，完成源文件调整、启动启用 Store 后重新读取确认。
- [ ] 只有来源清理完成且实际摘要一致才开放 Store 编辑；迁移中断保留恢复包，并允许回到原文件模式。
- [ ] 暂不支持迁移的模板/复杂插件配置保持原生只读管理，明确列出未纳管项。

验收：禁用/删除 Store 条目不会意外激活文件同名项；迁移前后有效配置等价；
Store 未启用、外部编辑和来源漂移均阻止错误应用。

### P2-02 应用状态机、版本与最小审计

- [ ] 定义配置 operation ID、目标节点/Service、base revision、candidate digest、创建者、期限与幂等键。
- [ ] revision 覆盖规范化的完整有效来源及必要原始文件摘要；不能只用主控数据库版本发现本地编辑。
- [ ] 持久化状态：`draft → validated → prepared → applying → verifying → confirmed`。
- [ ] 定义分支：冲突/校验拒绝、应用失败、`outcome_unknown`、`rolling_back → rolled_back/rollback_failed`、应用前取消。
- [ ] 网络超时不直接判失败；按 operation ID、摘要和 Agent 本地记录恢复核对，禁止盲目重新应用。
- [ ] 在任何写入前持久化最小审计与私有恢复快照；不能记录审计或恢复信息时不开始写操作。
- [ ] SQLite 增量迁移保留现有节点、令牌、绑定、流量和分组；提供迁移前备份及向旧二进制回退的明确要求。
- [ ] 同步现有备份/恢复的 schema 校验和最小托管安装格式，使 Store、事务日志与恢复快照在 G2 前可备份恢复；完整 includes/外部依赖图在阶段三扩展。

影响：`monitor/control/schema.sql` 与迁移代码、拟新增配置操作服务、Agent 本地操作日志。
验收：同一请求重试不重复写入；并发操作有明确冲突；重启后恢复进行中的操作；
审计中不保存密钥明文，数据迁移测试覆盖当前 schema v6 和已有受支持旧库路径。

### P2-03 管理能力与跨端命令

- [ ] 定义配置管理 capability（建议名 `config.manage.v1`）及 prepare/apply/query/rollback 等有界方法。
- [ ] 复用经过认证的独立 WSS；Agent 本地启用、主控管理会话授权和能力协商三者均满足才允许写入。
- [ ] 节点 Token 只证明节点身份；Agent 自报 capability 不能自行获得管理员权限或替其他节点执行操作。
- [ ] 请求绑定目标节点/Service、操作 ID、期望 revision、会话及期限；校验重放、过期、旧会话和重复请求。
- [ ] 每节点只允许一个正在执行的配置事务；断线后通过持久操作状态恢复，不无限缓存待执行命令。
- [ ] 明确禁用管理、节点撤销、Token 轮换和管理员注销时，对未执行与已执行操作的不同处理。
- [ ] 不开放任意命令、任意文件路径、任意 URL 拉取或替换启动凭据的能力。

影响：`shared/`、`agent/service/`、新配置执行包、`monitor/admin.go` 及操作协调器。
验收：旧 Agent 只读、未授权拒绝、CSRF、跨节点请求、重放、过期、断线、撤权与资源限额。
配置通道繁忙或失败不能阻塞主机采样和隧道转发。

### P2-04 原生校验与脱敏预览

- [ ] 对整套候选 Proxy/Visitor 调用锁定版本的原生类型解析、Complete 和验证逻辑，不仅检查 JSON 语法。
- [ ] 校验在目标 Agent 执行，使用其实际 FRP 版本、启动参数、unsafeFeatures 和模板环境；disabled 项也校验，主控预检不能替代本地校验。
- [ ] 校验名称、来源冲突、类型、端口/域名、引用、`start` 筛选、可用能力及不支持字段。
- [ ] 将本地配置有效、服务端策略可能拒绝和实际业务可达性分开呈现；预检不能承诺远端资源一定可用。
- [ ] 展示规范化 diff：新增/修改/删除/启停、影响对象、潜在连接重建、验证警告、基础版本与候选版本。
- [ ] 秘密字段使用保持/替换/清除语义，脱敏占位符不能作为真实值写回。
- [ ] 第一版保留已有秘密在 Agent 本地；需要新秘密时使用写入专用流程和本地私有引用，主控不持久化明文候选。
- [ ] 无法无损处理的高级字段拒绝编辑；原生 file/store 名称与 unknown 字段的处理策略写入测试。
- [ ] 校验和预览不修改 Store、原文件、运行实例或配置修订号；应用前再次校验并进行 CAS。

验收：错误配置无副作用；过期预览返回冲突；秘密不进入普通 GET、diff、日志、审计或前端持久存储；
JSON/TOML/YAML 的原生读取能力不被 Plus 的编辑模型误替代。

### P2-05 Agent 本地安全应用与恢复

- [ ] 增加窄接口适配器，支持整套 Store 配置准备/替换/恢复；不能用多次原生 CRUD 冒充事务。
- [ ] 加入同目录临时文件、唯一临时名、文件及目录同步、原子切换和原始权限检查；限制到固定管理根目录。
- [ ] 本地记录旧/新 digest、操作阶段和私有快照，使磁盘写入、内存来源更新、reload 之间的崩溃可判定。
- [ ] 所有受支持的 Store 写入入口与 Plus 操作共用串行化/版本检查，防止原生 Dashboard 并发写绕过锁。
- [ ] 检测外部文件编辑；第三方修改无法纳入锁时按漂移中止，不覆盖未知新版本。
- [ ] 文件更新后只调用一次整集运行时应用；reload 失败恢复 Store、内存源和运行配置，再验证恢复结果。
- [ ] 在原生启动读取 Store 之前检查并恢复未完成操作，再装载配置和报告状态；不能仅把恢复放到稍后启动的 telemetry goroutine。
- [ ] 恢复日志和快照不依赖监控连接持续在线；启动时不能判定安全版本则阻止不确定配置生效并提供本机修复入口。
- [ ] 保持锁范围有界，避免把磁盘同步或网络等待放入 FRP 转发锁；添加故障注入与并发检查。

验收：磁盘满、只读目录、持久化失败、切换后崩溃、reload 失败、外部并发编辑、重复命令、
进程强杀与重启；不会出现界面已成功但磁盘与运行态永久分离的静默状态。

### P2-06 结果确认与回退

- [ ] 分开报告“配置已持久化”“运行时已加载”“代理已登记/Visitor 已监听”“业务连通已验证或未测试”。
- [ ] 使用新配置摘要、Agent 实际运行快照及适用时的服务端观察共同确认；reload 返回 nil 不等于健康。
- [ ] 对禁用/删除操作验证对象已经撤下；对 Visitor 不要求不存在的服务端代理登记，对 XTCP 不编造 P2P 成功。
- [ ] 明确验证期限、自动回退条件和可选的已授权连通测试；正常等待连接与确定配置错误分开处理。
- [ ] 事务超时由 Agent 本地看门狗处理；主控断线后显示“结果未知”，重连查询真实结果。
- [ ] 自动或手工回退均生成可追踪操作，恢复旧摘要并重新核对运行态；若发现外部漂移，不强行覆盖。
- [ ] 回退失败保留 `rollback_failed`、阶段、实际状态及本机恢复步骤，不显示为“已恢复”。

验收：端口冲突、服务端拒绝、Visitor 启动失败、网络断开、确认消息丢失、主控重启、
回退途中退出；在恢复连接后能判断最终版本，不能因旧快照误判成功。

### P2-07 配置管理界面与原生文件维护边界

- [ ] 新建、编辑、复制、启用、禁用、删除、改名均生成草案；改名作为一个操作内的删除与新增，Proxy 与 Visitor 分别标识。

验收：完整“编辑 → 校验 → 预览 → 应用 → 确认 → 回退”浏览器与真实二进制流程；
