# frp-plus 开发计划

更新日期：2026-10-03（Asia/Shanghai）

状态：开发中；阶段一 G1、阶段二 G2 已通过本机验收，阶段三开始开发。写管理默认关闭，G3 尚未通过。任务勾选以实际验证为准，不代表已经上线。

实施基线：`upstream.lock` 固定的 FRP v0.71.0；升级上游版本另行评估，不与功能开发混合。

## 1. 目标与实施顺序

按以下顺序推进，每个阶段通过验收后再开放下一阶段的用户能力：

1. **补齐观察详情**：远端入口、Visitor、错误原因、传输方式，以及明确的原生配置管理入口。
2. **建立配置操作闭环**：配置来源明确，完成校验、变更预览、应用、结果确认和回退。
3. **补齐运维与验证**：配置变更审计查询、隧道历史、完整备份依赖和实际使用协议的互通回归。

阶段 2 开放任何写操作前，必须先完成最小审计记录、私有恢复快照和崩溃恢复能力；
阶段 3 再补齐审计检索、导出、保留策略和完整运维体验。不能将写操作的审计推迟到阶段 3。

最初规划提交为 `23851a2`，后续开发按本计划推进。稳定的功能说明、配置示例和操作手册
汇总到根目录 `README.md`，本文件用于跟踪任务、验证证据与尚未完成的工作。
本轮 G1/G2/G3 改动尚未部署生产；既有线上环境与开发验收基线分开记录，见 1.4。
用户已明确本次按 **1 个主控、10 个 Agent 一次性直接替换**，不要求灰度、滚动升级或
长时间稳定性验证；当前上线目标为 Linux amd64。保留必要的功能检查、数据备份与失败回退。

### 1.1 规划时基线事实

- 二进制仍由原生 `cmd/frpc` / `cmd/frps` 构建，补丁增加生命周期、配置段和只读快照。
- Plus 当前只管理监控节点、绑定、分组、套餐与探测，没有隧道配置写入和远程 reload 闭环。
- 现有 FRP 上报没有 Visitor、远端入口和完整错误模型；服务端只观察当前内嵌 frps。
- 监控协议严格拒绝未知字段，首个 hello 已包含旧 FRP 快照；新增字段必须考虑双向滚动升级。
- 原生 Store 单项 CRUD 的磁盘持久化与运行时 reload 不是一个事务；reload 失败不会自动恢复磁盘。
- 原生文件配置 PUT 只是写文件，不能直接作为“校验并安全应用”接口使用。
- 文件与 Store 同名时存在来源覆盖；禁用或删除 Store 条目，可能使文件中的同名条目重新生效。
- 原生 frpc reload 不等于替换全部启动配置；frps 没有同等的配置热重载入口。
- 当前备份工具依赖安装格式和固定文件白名单，拒绝 includes；现有协议测试不是完整原生功能矩阵。

代码依据：`shared/protocol.go`、`shared/frpserver.go`、`monitor/reconcile.go`、
`patches/0001-monitor-lifecycle.patch`、`patches/0004-frp-reconciliation.patch`、
`scripts/frp.py`、`scripts/ops.py`、`tests/frp_smoke.py`。
原生管理实现以锁定源码的 `client/config_manager.go`、`client/service.go`、
`pkg/config/source/store.go`、`pkg/config/source/aggregator.go` 为核查入口。
`.cache` 只是组装目录，不作为提交内容或唯一设计依据；每轮实现重新核对锁定源码和补丁。

### 1.2 首版范围与设计决策

| 事项 | 计划采用的决策 | 边界 |
|---|---|---|
| 可写配置来源 | **原生 Store 作为首版 Proxy/Visitor 的唯一托管来源** | 沿用 FRP 类型、校验和运行机制，增加整集应用与恢复适配层 |
| 已有文件配置 | 先只读盘点、展示有效配置与来源；提供显式迁移到 Store 的流程 | 不自动接管，不通过覆盖同名项实现迁移；文件保持原生管理能力 |
| 启动配置 | serverAddr、认证、TLS、telemetry、monitor、Store 路径、frps 监听等仍由原生文件管理 | 展示需重启提示、校验与维护说明；首版不承诺远程热改这些字段 |
| 原生 Dashboard | 保留，并提供明确的访问条件和经管理员设置的入口 | 不要求公网开放，不将其凭据下发到浏览器，不自动反向代理任意地址 |
| 控制通道 | 在现有独立 WSS 上协商专用配置管理能力 | 仅显式启用托管的 Agent 接收；旧 Agent 保持只读，不增加任意 shell 执行 |
| 配置权威 | Agent 本地 Store 与运行时实际状态是应用结果依据 | 主控保存操作意图和状态，不把数据库里的期望值当作已生效配置 |
| 数据持久化 | SQLite 保存操作、审计和事件；现有可选 TSDB 保存指标曲线 | 私有回退快照与脱敏审计分离；历史关闭不影响配置操作与审计 |
| 管理范围 | 当前内嵌 frps 与逐节点的单个明确 frpc Service | 跨 frps 汇总、多 Service 托管及远程进程升级不纳入首版 |
| 套餐与流量 | 延续主机账本与 FRP 隧道流量分开统计 | 不附带实现超额断网、自动限速或到期停隧道 |

对不支持的类型、字段、旧版本和配置来源，界面必须明确说明原因，不能显示一个实际无效的保存按钮。
首版未覆盖的高级配置应完整保留或拒绝编辑，禁止解析后静默丢弃再写回。

### 1.3 实施核查补充（阶段二前置约束）

- 原生 Store 的 `Load()` 读取内存；只有初始化 `loadFromFile()` 读取磁盘。
  外部 Store 文件编辑不能靠原生 reload 自动发现或生效，托管 CAS 必须同时检查原始磁盘摘要。
- 原生 Store 装载允许未知字段，重复名称写入 map 时后项覆盖。不能通过当前 typed 对象
  证明原文无损；迁移前必须严格解析原文，拒绝未知字段、重复名称和不可保留的高级内容。
- 阶段一的观察 revision 仅覆盖聚合后有效对象、来源类别和 `start`，不包含被覆盖内容、
  主文件原文、完整启动 common 或依赖文件；阶段二必须单独定义完整 CAS revision。
- 原生 Proxy/Visitor 的部分秘密是内联字符串，没有通用 secretRef。Plus 的本地引用层
  需要在 Agent 解析；最终原生 Store 及回退材料仍可能包含秘密，必须使用私有文件权限，
  不能宣称原生配置已加密，也不能将脱敏 GET 当作完整候选回写。
- `reloadMu` 只串行一个 Service，原生文件 PUT 不持有该锁。所有受支持写入口需共同
  进入托管屏障；同 Store 多 Service/多进程须拒绝并持有跨进程独占锁。
- 不遵守锁的外部编辑无法仅靠“读摘要后 rename”消除竞态。托管根目录须约定独占写入，
  手改前退出托管；CAS 前后复核、保存发现的漂移、遇到不确定性中止，明确保证范围。

### 1.4 既有部署基线与本轮验证范围

2026-10-03，用户指定私有 `.env.serverlist` 为部署资料来源。该文件包含多次历史记录，
以后段最新部署记录为准；文件未被 Git 跟踪且已 ignored，不将其地址、域名、凭据、
节点名称或真实备份路径复制到公开文档。当天已对清单内全部 10 台机器进行只读核验，
没有修改服务、配置、数据库或反向代理，没有部署或重启。

| 项目 | 本次核验结果 | 证据边界 |
|---|---|---|
| 部署规模 | 1 个主控、10 个 Agent，均为 Linux amd64；主控与其中一个 Agent 同机 | 10 台机器 SSH 只读核验，11 个 systemd 服务 active/running，重启计数为 0 |
| 主控版本 | `da9600f` | 实际进程发布目录和二进制 SHA256 与最新私有记录一致 |
| Agent 版本 | 全部 `43e3294` | 10 个实际进程的发布目录和二进制 SHA256 一致，并匹配私有记录 |
| 当前监控 | 10/10 online、fresh、FRP connected | 本次读取主控实时公开节点 API；不据此推断任意业务隧道可用 |
| FRP 控制能力 | Token 认证，Agent 显式启用 TLS；协议、wire、复用采用默认值 | 对照相同的锁定上游 v0.71.0，默认分别为 TCP、v1、TCPMux=true；未进行握手抓包 |
| 监控传输 | 10 个 Agent 均配置独立 WSS | 配置与当前运行进程的配置路径一致，文件修改时间早于进程启动 |
| 原生配置来源 | 10 个 Plus Agent 的主配置均无 Proxy、Visitor、includes 或 Store | 不代表同机独立原生 FRP 服务没有业务；本次未盘点那些独立服务的业务配置 |
| 托管配置 | 全部未开启 | 直接替换全部服务；是否启用 Store 仍作为显式配置选择 |
| 数据库与历史 | 线上二进制使用 schema v6；SQLite 主文件头为 v6；配置启用 TSDB，保留 90 天 | 仅读取数据库主文件头，未把它当成活跃 WAL 的一致性或完整性检查；历史数据恢复仍待专项验证 |

版本兼容核查：现有旧 Plus 测试基线 `23851a2` 与线上 Agent `43e3294`、主控 `da9600f`
的 `shared/`、`agent/service/`、`monitor/service.go`、`monitor/control/`、`patches/`、
`upstream.lock` Git 对象完全一致。因此既有新旧四组合测试具有线上旧协议实现的源码等价
依据，但没有执行过此次候选版本的 Linux 现场升级，不能用本机结果替代现场验收。

据此确定以下后续门禁：

1. **现有能力升级回归**：Token + TCP/TLS + wire v1 + 复用、独立 WSS 上报、10 节点
   持续在线与采样新鲜、身份/凭据/分组/套餐/精确账本保留、90 天历史的旧样本可读与新样本
   续写；保持同机独立原生 FRP 服务的运行状态。
2. **隔离功能回归**：线上这批 Agent 没有 Proxy/Visitor 业务，不能用空列表完成转发验收。
   八类 Proxy、三类 Visitor、其他控制传输、OIDC、插件、Store 应用与回退、故障恢复，
   继续按 P3-05 在隔离环境验证。ARM64 和复杂 NAT 单独记录证据边界，不作为本次
   Linux amd64 直接替换的上线前置。
3. **升级与降级演练**：已验收的本机 G2 为 schema v9；正在开发的审计会引入 v10，
   后续历史还会改变数据结构。以候选版本最终 schema 为准，从真实 v6 结构进行数据保留
   演练；升级前完整备份 SQLite/WAL、TSDB、配置依赖、凭据和服务信息。旧部署中仅切换
   网页二进制的回退说明不适用于本轮数据库迁移，必须验证匹配数据版本的恢复路径。

私有核验脚本和脱敏原始结果保存在 ignored 的 `.cache/deployment-inventory/`。
本节完成部署能力盘点，不代表 G3 通过，也不代表新功能已经上线。

**部署约束补充**：用户授权上述 11 个服务直接替换，不需要分批试点或持续观察门禁。
实施时先保存与当前二进制匹配的配置、数据库和历史备份，再替换主控与全部 Agent，
启动后核对服务状态、10 节点上报、历史读取与新增功能；失败时按匹配的数据版本恢复。
不为灰度、滚动混合版本、长时容量或未使用平台额外扩展实现。配置事务、审计、历史与
完整备份依然属于本轮明确交付内容；“直接替换”不改变配置来源和实际生效结果的核对要求。

## 2. 阶段一：补齐观察详情

交付目标：管理员能回答“这条代理或 Visitor 从哪里访问、采用什么传输、为什么异常、
配置来自哪里、下一步在哪里修改”，同时保留原生客户端与旧 Agent 的兼容性。

### P1-01 协议演进与私有详情契约

- [x] 定义独立详情能力 `frp.detail.v1`，与原生 wire v1/v2 分开命名。
- [x] 首个 hello 保持旧结构；通过已认证升级响应头预告能力，Agent 仅在得到预告后声明、协商接受后发送新详情方法；旧服务端不收到新增字段或能力。
- [x] 新服务端继续接受旧 Agent；新增详情使用独立 DTO/方法及时间、新鲜度和错误状态，携带 session/sequence 并与指标、探测共享单调序号空间。
- [x] 服务端仅返回客户端已声明能力的受支持子集；同时更新两端编解码与下行分发，避免旧版 Agent 因未知方法断开。
- [x] 定义 Proxy、Visitor、入口、传输、来源、错误等私有 DTO，避免直接序列化原生配置对象。
- [x] 为数量、帧大小、字符串长度、采样频率设置上限；超限显示“不完整/不可用”，主机指标继续上报。
- [x] 新详情仅进入管理 API；列表/SSE 仅发布状态和时间，完整数据按节点鉴权读取。现有公开 FRP 汇总保持原边界，不顺带暴露更多字段。

影响：`shared/protocol.go`、`shared/browser.go`、`agent/service/service.go`、`monitor/service.go`。
验收：新旧 Agent/Server 四组合、未知能力、未协商方法、重复/迟到帧、超限和断线重连；
旧端不因新增字段退出，公开 JSON/SSE 不包含新增私有详情。

### P1-02 远端入口与有效地址

- [x] Proxy 详情区分配置期望、服务端实际分配、管理员公布入口，并标注各自来源和观察时间。
- [x] TCP/UDP 采集实际监听地址和端口，包括动态分配端口；离线或未登记时不沿用旧端口冒充当前值。
- [x] HTTP/HTTPS/TCPMUX 展示域名、子域名、相关服务端端口和路由摘要；支持多入口及 IPv6。
- [x] STCP/SUDP/XTCP 显示通过 Visitor 访问，不生成不存在的公网 URL。
- [x] 增加管理员公布访问地址的可选配置；监听地址、回环地址、通配地址不直接等同公网可达地址。
- [x] 保留服务端独有代理与原版 frpc 的展示；缺少 Agent 详情时标记“仅服务端观察”。

影响：新增顺序补丁扩展原生快照、`shared/frpserver.go`、`monitor/reconcile.go`、管理 DTO。
验收：固定/动态端口、IPv4/IPv6、多域名、反代/NAT、禁用、离线、同名不同归属；
不能根据旧快照或通配地址错误拼接访问链接。

### P1-03 Visitor 独立状态

- [x] 新增独立 `visitors` 模型，记录名称、类型、serverUser/serverName、本地监听、启用状态和运行阶段。
- [x] 在原生 Visitor Manager 增加有界只读快照及最近启动/连接错误记录，覆盖创建、重试、重载与关闭。
- [x] 分开表示“本地监听成功”“远端连接已建立”“P2P 已建立”和“fallback 生效”，未知值保持未知。
- [x] 展示 XTCP 的穿透/fallback 摘要；不得把 Visitor 计入服务端 Proxy 注册数。
- [x] 服务端无法独立核对的 Visitor 显示数据来源与验证局限，不通过名称猜测跨节点归属。

影响：原生 `client/visitor/` 补丁、`shared/protocol.go`、Agent 适配器、管理页面。
验收：STCP/SUDP/XTCP、端口占用、目标缺失、密钥不匹配、fallback、禁用、删除、
原生允许的非监听模式；没有实际连接时不能宣称服务端可达。

### P1-04 错误原因与传输摘要

- [x] 控制连接、代理注册、健康检查和 Visitor 分别记录错误 code、stage、发生时间、恢复时间和安全摘要。
- [x] 优先映射稳定错误码，再提供脱敏、限长的说明；不原样透传日志、配置或下游完整错误字符串。
- [x] 分开展示 FRP 控制传输 TCP/KCP/QUIC/WS/WSS、wire v1/v2、TLS、代理加密/压缩和连接复用。
- [x] 区分配置值与实际观测值；无法确认实际协商结果时明确注明。
- [x] 普通插件仅显示类型及允许的摘要，不上传任意插件选项、Header、Token、OIDC claims、密钥或证书内容。

验收：恢复后旧错误不再被当作当前故障；含凭据 URL、换行、超长文本和 HTML 的错误均被处理；
公开 API、日志、审计和指标标签没有秘密信息。

### P1-05 配置来源与原生管理入口

- [x] 显示配置来源：主文件、include、Store，以及合并后的实际生效来源；显式提示重复名称与覆盖。
- [x] 显示来源修订摘要、最后读取时间、只读/托管状态、支持能力和是否需要重启。

- [x] 原生配置路径等敏感运维信息仅向管理员展示，前端不持有原生 Dashboard 密码。

## 3. 阶段二：建立配置操作闭环

交付目标：管理员能对已授权节点的托管 Proxy/Visitor 完成一次可追踪、可确认、可恢复的配置变更。
原生进程重新建立代理可能造成连接中断，界面必须展示影响，不能承诺运行时无缝或跨节点原子事务。
